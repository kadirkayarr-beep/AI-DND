AI-DND — MASTER PROJECT VISION & ARCHITECTURE CHARTER

===============================================================
1 — WHAT ARE WE BUILDING?
===============================================================

We are building a local AI-powered Dungeons & Dragons style RPG.

This is NOT:

- a simple chatbot pretending to be a Dungeon Master
- a rigid text adventure with predefined commands
- a Python game that merely prints scripted responses
- an AI model that is allowed to invent mechanical truth
- a finite branching-choice adventure

The goal is:

A persistent, open-ended, rule-governed fantasy world where the player
can type almost anything in natural language, and the game responds
consistently, creatively and mechanically correctly.

The player should feel like they are talking to a human Dungeon Master.

At the same time, the world must have actual state and actual rules.

===============================================================
2 — CORE PHILOSOPHY
===============================================================

The central rule of the entire project is:

PYTHON DECIDES REALITY.
AI UNDERSTANDS INTENT AND DESCRIBES REALITY.

These responsibilities must remain separate.

AI should be creative.

Python should be authoritative.

Neither layer should attempt to replace the other.

===============================================================
3 — THE DESIRED PLAYER EXPERIENCE
===============================================================

The player should be able to write naturally.

Examples:

"Şehre giriyorum."

"Şöyle bi etrafa bakıyorum."

"Random ne var etrafımda?"

"Barmene selam veriyorum."

"Masadaki adama neden üzgün olduğunu soruyorum."

"Kapıyı açmaya çalışıyorum."

"Kapının kilidini inceliyorum."

"Kılıcımı çekip hayduta saldırıyorum."

"Ormana doğru gidiyorum."

"Ben bu adamı daha önce görmüş müydüm?"

"Bana geçen gün ejderhadan bahsetmiş miydin?"

"Bu tavernada kimler var?"

"Nerdeyim lan?"

The player should NOT need to memorize commands such as:

LOOK
MOVE TAVERN
TALK BARTENDER
ATTACK NPC_001

The game must understand ordinary Turkish,
slang,
minor spelling errors,
different sentence structures,
and unexpected wording.

===============================================================
4 — NATURAL LANGUAGE UNDERSTANDING
===============================================================

AI should be the primary semantic language-understanding layer.

Python must NOT become a giant Turkish phrase dictionary.

Do not solve natural language by continuously adding:

if "etrafta ne var"
elif "etrafımda ne var"
elif "çevremde ne var"
...

Deterministic patterns are useful for:

- obvious fast paths
- safety rules
- known aliases
- mechanical protection

But the AI model should understand that:

"etrafta ne var"

"random ne var etrafımda"

"abi bi çevreye bakalım"

"buralar ne alemde"

"şöyle sağa sola bakıyorum"

all broadly mean:

EXPLORE / OBSERVE.

Likewise:

"tavernada kimler var"

must mean:

QUERY / PRESENCE

not:

TRAVEL TO TAVERN.

Mentioning a location does not imply movement.

===============================================================
5 — INTENT LAYER
===============================================================

Every player message should first become a structured semantic intent.

Conceptually:

PLAYER TEXT
    ↓
AI INTENT PARSER
    ↓
STRUCTURED INTENT
    ↓
PYTHON VALIDATION

Example categories may include:

travel
explore
query
dialogue
attack
inventory
world_interaction
skill_check
rest
use_item
narrative

Useful subtypes:

query:
- self
- location
- presence
- npc_identity

explore:
- observe
- inspect
- search

travel:
- intended
- completed

The exact schema may evolve.

The important principle is:

AI interprets meaning.
Python decides whether the interpreted action is legal and what actually happens.

===============================================================
6 — OBSERVE VS INSPECT VS SEARCH
===============================================================

These must not be treated as the same mechanic.

OBSERVE:

"Ne görüyorum?"
"Etrafta ne var?"
"Şöyle bi bakıyorum."

This usually requires NO roll.

It is ordinary perception of obvious surroundings.

INSPECT:

"Kapıyı yakından inceliyorum."
"Heykele dikkatlice bakıyorum."

This may simply reveal visible details.

A roll is only needed if a meaningful uncertainty exists.

SEARCH:

"Odanın içinde gizli geçit arıyorum."
"Çekmeceleri gizli bir şey için araştırıyorum."

This may trigger:

Investigation
Perception
or another relevant mechanic.

Never force dice rolls for normal questions or casual observation.

===============================================================
7 — PYTHON RULE ENGINE
===============================================================

Python owns mechanical reality.

Examples include:

- dice rolls
- ability modifiers
- proficiency bonus
- AC
- HP
- damage
- critical hits
- initiative
- skill checks
- DC
- inventory
- equipped/drawn state
- door state
- lock state
- combat state
- player location
- canonical NPC IDs
- canonical location IDs
- world-state mutation
- unconscious/death state
- movement
- persistent features
- item ownership

AI must NEVER independently decide these.

AI may say:

"The attack cuts across the bandit's shoulder."

only if Python has already determined that the attack hit.

AI may NOT decide:

- whether the attack hit
- how much damage occurred
- whether the door opened
- whether the player owns an item
- whether an NPC is unconscious

===============================================================
8 — ACTION RESULT
===============================================================

Python should convert validated intents into structured results.

Conceptually:

{
    action: "attack",
    status: "resolved",
    success: true,
    target_id: "npc_004",
    attack_roll: 17,
    damage: 6,
    outcome: "hit",
    state_changes: [...]
}

or:

{
    action: "explore",
    explore_type: "observe",
    status: "resolved",
    success: true,
    state_changes: []
}

Important:

NO STATE CHANGE DOES NOT MEAN NO GAMEPLAY.

Looking around may change nothing mechanically,
but still deserves meaningful narration.

===============================================================
9 — AI NARRATOR / DUNGEON MASTER
===============================================================

After Python resolves reality, the narrator receives:

- player input
- structured intent
- action result
- current location
- registered NPCs
- known features
- inventory
- combat state
- relevant memory
- relevant world facts

The narrator's job is to turn that into natural fantasy storytelling.

It should feel like a Dungeon Master.

Not like:

"Python durumu güncellendi."

Not like:

"Belirttiğin eylem dışında sahnede yeni bir değişiklik olmaz."

unless a genuine safety fallback is required.

Narration should be:

- atmospheric
- concise enough to keep gameplay flowing
- context-aware
- varied
- natural
- responsive to unusual player behavior

===============================================================
10 — THE AI MUST BE ALLOWED TO PARAPHRASE
===============================================================

Narrator safety must not require literal verb equality.

Example:

Player:

"Tavernaya gidiyorum."

Python determines:

travel completed → tavern.

Narrator may naturally say:

"Tavernaya ulaşırsın."

"Kısa yürüyüşün ardından tavernaya varırsın."

"Tavernanın kapısından içeri girersin."

These all describe the same committed action.

But the narrator may NOT invent additional player decisions:

"Masaya oturursun."

"Bira sipariş edersin."

"Kılıcını çekersin."

"Barmene para uzatırsın."

unless those actions were actually chosen/resolved.

We want:

semantic freedom

without:

player-control theft.

===============================================================
11 — WORLD STATE
===============================================================

The world must actually exist outside the narrator's prose.

Persistent canonical state should include concepts such as:

locations
NPCs
features
doors
items
ground items
inventory
combat
events
flags
relationships
memories

Examples:

If the bartender is named Rurik,
leaving the tavern and returning later must not create a different bartender.

If a sword is dropped in the forest,
it must remain in the forest.

It must not magically appear in the castle.

If a door was opened,
it stays open unless something changes it.

If an NPC has 3 HP,
the narrator cannot later pretend they have full HP.

===============================================================
12 — DYNAMIC WORLD GENERATION
===============================================================

The world must NOT be completely hardcoded.

We do NOT want Python containing permanent lists such as:

bartender_names = [...]
forest_bandits = [...]
castle_guard_names = [...]

AI may propose:

- new NPCs
- locations
- scene features
- descriptions

Python then validates those proposals and assigns canonical IDs.

Example:

AI proposes:

Name: "Thorin"
Role: "Barmen"

Python accepts and creates:

npc_017

From that point onward:

npc_017

is canonical truth.

The AI is no longer free to randomly replace him.

===============================================================
13 — LOCATION GENERATION
===============================================================

The same principle applies to locations.

The player should be able to say:

"Neverwinter'a gidiyorum."

"Eski Ay Kulesi'ne gidiyorum."

"Yakındaki terk edilmiş madene doğru ilerliyorum."

Unknown-but-valid locations may be dynamically proposed.

Python assigns:

location_001
location_002
...

Locations then persist.

The player's movement must always be committed by Python.

===============================================================
14 — SCENE REALIZATION
===============================================================

Entering a location should feel like entering a place.

Successful travel into a new or empty location should usually allow one
creative narrator/world-generation pass.

The AI may propose context-appropriate:

NPCs
features
atmosphere

Example:

The player enters a tavern.

Possible canonical proposals:

- bartender
- fireplace
- long wooden bar
- suspicious traveler

Not every possible detail needs to become persistent.

Temporary sensory details may remain narrative-only:

rain tapping on windows
smell of food
crowd noise
dim candlelight

We must distinguish:

CANONICAL WORLD FACT

from:

TEMPORARY NARRATIVE ATMOSPHERE.

===============================================================
15 — NPC SYSTEM
===============================================================

NPCs should behave like persistent characters.

Each NPC may eventually have:

id
name
role
location
personality
knowledge
memory
relationships
attitude
combat stats
inventory
goals
faction
status

NPC references should be natural.

If a registered NPC has role:

Barmen

the player should be able to say:

"barmene selam veriyorum"

"barmenle konuşuyorum"

"barmene naber diyorum"

without knowing the NPC's internal ID.

Python resolves the canonical entity.

===============================================================
16 — NPC DIALOGUE
===============================================================

NPC dialogue should NOT sound like a database lookup.

NPCs should have personality.

The AI controls HOW NPCs speak.

Python controls WHO exists.

Example:

Python:

npc_002 = bartender, name Rurik.

Player:

"Adın ne?"

AI/NPC:

"Rurik. Şu köşedeki masalara bulaşmadığın sürece iyi anlaşırız."

But the AI cannot suddenly rename him Gromm.

===============================================================
17 — NPC MEMORY
===============================================================

NPCs must remember relevant interactions.

Memory must distinguish speaker attribution.

Example:

player_said:
"Benim adım Ardan."

npc_said:
"Ben Rurik."

Later:

"Daha önce sana adımı söylemiş miydim?"

NPC should recall Ardan.

But:

"Geçen gün bana ejderha hazinesinden bahsetmiştin."

must NOT become true unless that NPC actually said it.

Player claims are not world facts.

False-memory protection is essential.

===============================================================
18 — PLAYER ASSERTIONS ARE NOT AUTOMATIC TRUTH
===============================================================

The player may say:

"Karşımda bir ejderha görüyorum."

"Burada on asker var."

"Barmenin adı Gromm."

"Masada efsanevi bir kılıç var."

These statements alone must NOT modify canonical reality.

The player controls their character's actions.

The player does NOT author world truth.

The game may interpret these as:

assumptions
questions
roleplay
attempted interactions

but Python must validate reality.

===============================================================
19 — QUERY SYSTEM
===============================================================

The player should be able to ask questions naturally.

SELF:

"Ben kimim?"
"Benim adım ne?"
"Karakterimin sınıfı ne?"

LOCATION:

"Neredeyim?"
"Nerdeyim?"
"Buranın adı ne?"

PRESENCE:

"Burada kim var?"
"Tavernada kimler var?"
"Kim var lan etrafta?"

NPC IDENTITY:

"Adın ne?"
"Sen kimsin?"

Context must matter.

"Adın ne?"

while talking to an NPC

should normally refer to that NPC.

===============================================================
20 — INVENTORY
===============================================================

Inventory must be authoritative.

The player cannot use items they do not possess.

Dropped items should be location-scoped.

Example:

Drop sword in forest.

Travel to castle.

"Yerdeki kılıcı alıyorum."

must NOT retrieve the forest sword.

Items cannot teleport because of language interpretation.

===============================================================
21 — DOORS / INTERACTIONS
===============================================================

Visible world objects must have persistent state.

A door may have:

open
closed
locked
broken

Normal unlocked door:

"Kapıyı açıyorum."

does not require a roll.

Locked door:

"Kapıyı açıyorum."

must not automatically open.

Forcing or lockpicking may require mechanics.

Looking at a door must not accidentally open it.

===============================================================
22 — COMBAT
===============================================================

Combat is Python-authoritative.

Current direction includes:

weapon validation
canonical targets
target location validation
attack rolls
AC
damage
natural 1
natural 20
HP
unconscious state
initiative
enemy retaliation
combat rounds
combat state

Combat narration is AI-generated,
but outcomes are entirely Python-generated.

Eventually combat may grow to support:

multiple enemies
ranged attacks
spellcasting
class abilities
conditions
movement
death saves
advantage/disadvantage

but these should be added incrementally.

===============================================================
23 — CURRENT COMBAT V2 DESIGN PRINCIPLE
===============================================================

The current simple encounter UX is roughly:

player combat command
    ↓
player attack
    ↓
if target survives:
enemy retaliation
    ↓
round advances

Initiative state exists and should remain internally consistent.

Future combat systems may become more sophisticated,
but do not prematurely turn the code into a massive combat simulator.

===============================================================
25 — MEMORY LAYERS
===============================================================

Long-term memory should ideally be separated into layers.

SESSION WORLD STATE:

exact mechanical truth.

NPC MEMORY:

what a specific NPC remembers.

WORLD HISTORY:

important persistent events.

PLAYER KNOWLEDGE:

what the player character has discovered.

NARRATOR CONTEXT:

only the information needed to narrate the current scene.

Do NOT dump the entire game history into every Qwen prompt forever.

===============================================================
26 — CONSISTENCY
===============================================================

Consistency is more important than flashy narration.

If the player asks:

"Barın adı ne?"

the NPC should not respond with their own name.

If the player returns after 20 turns:

NPC names
locations
relationships
door states
inventory
combat consequences

should remain consistent.

===============================================================
27 — AI CREATIVITY
===============================================================

At the same time, consistency must NOT kill creativity.

The AI should still be free to create:

interesting descriptions
NPC personalities
dialogue
rumors
quests
tension
humor
atmosphere
unexpected reactions
world flavor

The rule is not:

AI DOES NOTHING.

The rule is:

AI CREATES IDEAS.
PYTHON DECIDES WHAT BECOMES REAL.

===============================================================
28 — PLAYER FREEDOM
===============================================================

The game must never become:

"Choose:

1. Attack
2. Talk
3. Leave"

The player writes what they want.

Unexpected actions are part of the design.

Examples:

"I throw my boot at him."

"I pretend to be the king's tax collector."

"I lick the mysterious crystal."

"I challenge the bartender to arm wrestling."

The system should attempt to understand and resolve unusual actions rather
than reject them merely because no exact command exists.

If a mechanic is unsupported,
fail safely without corrupting the world.

===============================================================
29 — FAILURE SHOULD BE NATURAL
===============================================================

The game should avoid mechanical developer-style output during normal play.

Bad:

"This action is unsupported."

Better:

"You raise the weapon, but the game currently has no rule capable of resolving
that particular action."

Even fallback should preserve the illusion of a game when possible.

But fallback text must never lie about mechanics.

===============================================================
30 — MODEL CALL BUDGET
===============================================================

Performance matters because the game runs locally.

Target normal turn:

CALL 1:
intent understanding

CALL 2:
narrator / NPC dialogue / world proposals

Usually no more than two model calls.

Avoid chaining:

intent
entity extraction
location generator
NPC generator
narrator
safety rewrite
memory summarizer

for every single turn.

Python should do deterministic work cheaply.

===============================================================
31 — LOCAL MODEL
===============================================================

The project currently uses local Ollama + qwen3:8b.

Maintain compatibility with both typed and dictionary Ollama SDK responses.

Do not unnecessarily enable Qwen thinking for small intent tasks.

Intent parsing should be:

fast
low-temperature
structured
short

Narration can be more creative.

===============================================================
32 — SAVE / LOAD — FUTURE GOAL
===============================================================

Eventually the player should be able to close the game and reopen it.

Persistent save should preserve:

character
locations
NPCs
NPC memory
inventory
ground items
doors
combat-independent statuses
world flags
history

Save/load is not required to solve every current bug,
but the architecture should not make persistence impossible.

===============================================================
33 — TESTING PHILOSOPHY
===============================================================

This project needs multiple types of tests.

UNIT / DETERMINISTIC:

Python mechanics.

Examples:

damage
doors
inventory
combat
location state
memory rules

AI PIPELINE TESTS:

semantic intent
world-update validation
narrator safety

LIVE MODEL TESTS:

real qwen3:8b behavior

MANUAL GAMEPLAY:

actual human play session.

All four matter.

A system can pass:

100% unit tests

and still be a terrible AI Dungeon Master.

Manual play is therefore authoritative evidence of UX problems.

===============================================================
34 — TESTS MUST NOT DEFINE THE PRODUCT
===============================================================

Do not distort the game simply to make an old test pass.

When test and intended behavior disagree:

first determine whether:

production is wrong

or

test expectation is obsolete.

Never weaken assertions merely to make the suite green.

===============================================================
35 — BACKUP / PRODUCTION DISCIPLINE
===============================================================

Current production game.py must be treated carefully.

Historical backups are reference points.

Never blindly overwrite production from an old V10 backup.

Never run old patch scripts against production without review.

Debug scripts are not authoritative specifications.

===============================================================
40 — MOST IMPORTANT DESIGN QUESTION
===============================================================

Whenever adding or changing code ask:

"Should Python decide this,
or should AI creatively express this?"

If the answer concerns:

truth
rules
numbers
state
ownership
existence
mechanical consequences

=> PYTHON.

If the answer concerns:

language
personality
description
tone
creative detail
dialogue
interpretation

=> AI.

If it contains both:

AI proposes / interprets.

Python validates / commits.

AI narrates the committed result.
