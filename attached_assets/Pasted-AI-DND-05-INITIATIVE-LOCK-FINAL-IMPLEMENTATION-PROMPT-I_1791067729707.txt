AI-DND — #05 INITIATIVE LOCK
FINAL IMPLEMENTATION PROMPT

IMPORTANT:

#01 — Campaign Time V1 is COMPLETE.
#02 — Campaign Time Edge Cases is COMPLETE.
#03 — Combat Design Lock is COMPLETE.
#04 — Action Economy Lock is CURRENTLY IN PROGRESS.

This task implements and hardens the Initiative system.

Do NOT redesign:
- Campaign Time
- Campaign Time Edge Cases
- Combat lifecycle
- Action Economy
- Weapon/Attack mechanics
- Monster Combat
- Death System
- Spell system
- Persistence architecture
- UI architecture

Initiative must integrate with the existing systems rather than creating
parallel combat state.

==================================================
1. SOURCE AUTHORITY
==================================================

Use the uploaded:

D&D 5e — Player's Handbook 2024
D&D 5e — Dungeon Master Guide 2024
D&D 5e — Monster Manual 2024

as the primary rules references for Initiative.

Rules define the intended game mechanics.

Python remains the sole authority that resolves actual Initiative,
turn order, round progression, and combat state.

Qwen:
- may understand player intent,
- may narrate verified Initiative/combat events,
- must never determine Initiative results.

Frontend:
- may display Initiative order,
- may display whose turn it is,
- may display round information,
- must never calculate or mutate Initiative state.

==================================================
2. CORE INVARIANT
==================================================

INITIATIVE IS CANONICAL COMBAT STATE.

Python owns:

- Initiative rolls
- Initiative modifiers
- Advantage/Disadvantage
- Surprise effects
- Initiative totals
- Initiative order
- current actor
- current turn index
- round number
- joining combatants
- leaving combatants
- Initiative-triggered effects
- turn-boundary progression

Qwen and frontend cannot override any of these.

==================================================
3. COMBAT START OWNERSHIP
==================================================

#03 Combat Design Lock owns whether Combat has actually started.

Initiative must NOT independently start Combat merely because:

- an Initiative endpoint was called
- Qwen suggests Combat
- a hostile creature exists
- a player mentions violence
- the frontend displays a combat button
- a threat is present

Initiative begins only after the authoritative #03 Combat lifecycle
has established that Combat has started.

Preserve the existing explicit Combat-start/player-start contract.

Do not create a second Combat-start mechanism.

==================================================
4. INITIATIVE IS ROLLED ONCE
==================================================

For a normal Combat encounter:

1. Combat is authoritatively started.
2. Participants are established.
3. Initiative is rolled.
4. Initiative order is constructed.
5. Combat proceeds through that order.

Do NOT reroll Initiative:

- every round
- every turn
- after every attack
- after every Action
- after every Reaction
- after every movement
- after damage
- because HP changes
- because a target dies
- because the player changes intention.

The Initiative order remains stable from round to round unless an
authoritative rule explicitly changes the order.

==================================================
5. EXISTING RNG IS AUTHORITATIVE
==================================================

Use the existing authoritative Python RNG mechanism.

Do NOT create a second RNG implementation.

Do NOT use:

- Qwen-generated numbers
- frontend-generated numbers
- browser Math.random()
- timestamps
- hashes as fake dice
- deterministic pseudo-rolls replacing the existing RNG

The existing RNG progression must remain compatible with:

- combat
- rollback
- persistence
- action receipts
- save/resume.

Do not silently change RNG semantics.

==================================================
6. INITIATIVE ROLL
==================================================

The normal Initiative roll is:

d20 + applicable Initiative modifier.

For player characters, the normal underlying ability modifier is
Dexterity.

For monsters, use the Initiative modifier defined by the authoritative
monster data/stat block.

Do not hardcode:

initiative_modifier = Dexterity modifier

for every creature.

Specific features may add or alter the Initiative modifier.

Examples include features that:

- add Proficiency Bonus
- add Wisdom modifier
- grant Advantage
- otherwise modify Initiative.

These must be represented through the authoritative character/feature
system.

==================================================
7. INITIATIVE MODIFIER BREAKDOWN
==================================================

Where practical, retain enough structured information to audit the
result.

Conceptually:

initiative_roll:
- raw_d20
- base_modifier
- additional_modifiers
- advantage/disadvantage state
- final_total
- source/context

Example:

d20 = 14
Dexterity modifier = +3
Alert proficiency = +3

Initiative = 20

Do not require this exact data structure.

The invariant is:

Python must be able to explain how the canonical Initiative total was
produced.

==================================================
8. ADVANTAGE / DISADVANTAGE
==================================================

Initiative Advantage/Disadvantage must use the authoritative existing
D20/roll-resolution mechanism.

Do NOT create a separate Initiative-only implementation of
Advantage/Disadvantage.

Examples of possible Initiative Advantage sources include:

- class features
- feats
- magic items
- conditions
- other explicit rules.

Examples of Disadvantage include:

- Surprise at Combat start
- Incapacitated when Initiative is rolled
- other explicit authoritative rules.

Resolve all applicable sources before the roll is finalized.

Do not let Qwen decide whether Advantage or Disadvantage exists.

==================================================
9. SURPRISE — 2024 RULE
==================================================

IMPORTANT:

Do NOT import the old 2014-style:

"Surprised creatures automatically lose their first turn"

system.

For the 2024 rules used by this project, Surprise affects the Initiative
roll.

If a combatant is surprised by Combat starting:

Initiative roll = Disadvantage

The system must therefore represent Surprise at the time Initiative is
rolled.

After the Initiative roll:

do not continue applying a permanent generic "Surprised" penalty to
every subsequent turn unless another authoritative rule explicitly
requires it.

Do not create a legacy first-round skip system.

==================================================
10. SURPRISE DETERMINATION
==================================================

Surprise must be determined by authoritative Combat state before
Initiative is resolved.

Do NOT let:

- Qwen
- player prose
- frontend
- narration

retroactively declare a participant surprised after Initiative has been
rolled.

If the existing Combat lifecycle already determines awareness/surprise,
reuse it.

Do NOT create a second stealth/perception/surprise engine in Initiative.

If the required awareness information is unavailable:

do not invent it.

Use the existing authoritative Combat/world state and report the
limitation.

==================================================
11. INCAPACITATED AT INITIATIVE
==================================================

Preserve the 2024 rule that an Incapacitated creature has Disadvantage
when it rolls Initiative.

This must be evaluated at the moment Initiative is rolled.

Do NOT confuse:

"Disadvantage on Initiative"

with:

"remove this creature from the Initiative order."

An Incapacitated creature can still have an Initiative slot.

==================================================
12. GROUP INITIATIVE
==================================================

For a group of identical creatures that are being handled as one
authoritative group, use a single Initiative roll for the group when
the rules call for group Initiative.

All members of that group receive the same Initiative value.

Do NOT accidentally roll each identical monster separately when the
current combat rules define them as a group.

At the same time:

do not force unrelated creatures into one Initiative group merely
because they share a stat block.

The grouping must be authoritative.

==================================================
13. MONSTER INITIATIVE DATA
==================================================

Monster data must support:

- Initiative modifier
- Initiative score when present in authoritative stat data
- group Initiative where applicable.

Do NOT replace a monster's defined Initiative modifier with its
Dexterity modifier if the authoritative stat block provides an
additional modifier.

The Monster Manual explicitly allows monster Initiative modifiers to
include additional modifiers beyond Dexterity.

==================================================
14. INITIATIVE ORDER
==================================================

After all Initiative results are resolved:

sort participants from:

highest Initiative
↓
lowest Initiative

Store the resulting order as canonical combat state.

Conceptually:

initiative_order = [
    actor_A,
    actor_B,
    actor_C,
    actor_D
]

Do not recompute the order from current Dexterity values every turn.

The stored Initiative result controls the current Combat.

==================================================
15. TIE BREAKING
==================================================

The 2024 rules give the DM discretion over Initiative ties.

AI-DND requires deterministic canonical mechanics.

Therefore preserve the project's existing deterministic tie policy.

Current AI-DND policy:

PLAYER CHARACTER WINS A MIXED PLAYER/NPC TIE.

For other ties:

use a stable deterministic ordering mechanism already compatible with
the current combat implementation.

Do NOT:

- roll another random die for every tie
- use Qwen
- use frontend order
- use dictionary/hash iteration order
- use timestamps
- change tie order between reloads.

The same canonical Combat state must always produce the same tie result.

If the existing implementation already has a deterministic tie-breaker,
preserve it unless it directly violates this lock.

==================================================
16. TIE BREAKING MUST NOT CONSUME RNG
==================================================

Tie resolution must not consume a new random number.

This is important for:

- deterministic replay
- rollback
- save/resume
- RNG preservation
- debugging
- idempotency.

If two combatants roll:

15
15

the tie-break must resolve without changing the RNG stream.

==================================================
17. ALERT / POST-ROLL INITIATIVE EFFECTS
==================================================

The Initiative system must support authoritative features that modify
Initiative immediately after the roll.

Example:

Alert:

- adds Proficiency Bonus to Initiative
- can swap Initiative with a willing ally immediately after Initiative
  is rolled
- swap is unavailable if either participant is Incapacitated.

Do not hardcode Alert as the only possible post-roll effect.

Create/use a generic authoritative hook for:

AFTER INITIATIVE ROLL
and, where necessary,
AFTER INITIATIVE ORDER IS INITIALIZED.

The feature system owns the actual feature mechanics.

Initiative owns the ordering consequences.

==================================================
18. INITIATIVE-ROLL FEATURES
==================================================

Some features trigger when Initiative is rolled.

Examples include features that:

- regain a resource
- grant a bonus to Initiative
- grant Advantage
- grant another Initiative-related effect.

The Initiative system must expose a clean event boundary for:

ON_INITIATIVE_ROLL

and:

AFTER_INITIATIVE_ROLL

Do not implement every class feature in this task.

Do ensure the architecture cannot silently ignore valid existing
Initiative-triggered features.

==================================================
19. EXAMPLE: INITIATIVE MODIFIER FEATURES
==================================================

The implementation must be compatible with features such as:

- Alert Initiative Proficiency
- Barbarian Feral Instinct Advantage
- Gloom Stalker Initiative Bonus
- Bard features that modify Initiative.

These examples are architectural validation targets.

Do not copy their mechanics into Initiative code.

Their authoritative feature definitions must remain the source of truth.

==================================================
20. INITIATIVE ORDER MUST BE STABLE
==================================================

Once Combat starts:

initiative_order must remain stable between rounds.

Example:

Round 1:
A → C → B → D

Round 2:
A → C → B → D

Round 3:
A → C → B → D

Do NOT automatically reroll or resort because:

- Dexterity changes
- HP changes
- conditions change
- equipment changes
- player changes weapons
- a creature moves
- a creature attacks.

Only an explicit authoritative rule may alter Initiative.

==================================================
21. CURRENT TURN STATE
==================================================

The Initiative system must maintain an authoritative current turn.

Conceptually:

- round_number
- current_turn_index
- current_actor_id
- initiative_order

Do not duplicate this state in multiple independent systems.

#04 Action Economy must consume the current actor information from this
authoritative turn state.

==================================================
22. TURN ADVANCEMENT
==================================================

After the current actor's turn is legitimately complete:

advance to the next participant in Initiative order.

When the last participant completes their turn:

- increment round
- wrap to the first Initiative participant
- start the next round.

Do NOT advance the turn merely because:

- a player sent a request
- a model call completed
- narration completed
- a UI animation completed.

Turn advancement is a canonical mechanical operation.

==================================================
23. CURRENT ACTOR VALIDATION
==================================================

Every combat action must verify:

requested actor == current Initiative actor

before Action Economy or combat mechanics resolve.

Do not allow:

- out-of-turn attacks
- out-of-turn movement
- out-of-turn Actions
- out-of-turn Bonus Actions
- out-of-turn arbitrary turns

unless an explicit Reaction/Ready rule permits an off-turn response.

==================================================
24. REACTION COMPATIBILITY
==================================================

#04 owns Action Economy resources.

Initiative must provide the turn boundaries required by #04.

Do NOT duplicate Reaction reset logic in Initiative.

However, Initiative must correctly identify:

- start of actor's turn
- end of actor's turn
- transition to next actor
- transition to next round.

This allows #04 to correctly reset the Reaction at the start of that
creature's next turn.

==================================================
25. ACTION ECONOMY COMPATIBILITY
==================================================

#05 must not create a second Action Economy system.

When a new turn begins:

Initiative signals the turn boundary.

#04 initializes the appropriate:

- Action
- Bonus Action
- Movement
- Reaction
- Ready state

according to its own rules.

Do not duplicate these resources inside Initiative.

==================================================
26. UNCONSCIOUS / STABLE INITIATIVE SLOT
==================================================

CRITICAL AI-DND REQUIREMENT:

An actor becoming:

- 0 HP
- Unconscious
- Stable

must NOT automatically be removed from Initiative order.

The Initiative slot remains canonical unless the authoritative Death
System explicitly removes the participant from Combat.

Do NOT:

- skip the slot
- silently advance past it
- delete the actor from initiative_order
- reroll Initiative
- replace the actor with another participant.

If the current actor is Unconscious, the turn boundary must remain at
that actor so the Death System can perform its authoritative handling.

#08 Death System owns what happens during that turn.

#05 only owns the fact that the Initiative slot still exists.

==================================================
27. 0 HP DOES NOT END COMBAT
==================================================

Do not make:

HP <= 0
→ remove participant
→ end Combat

an Initiative rule.

The existing #03 Combat Design Lock and Death System behavior remain
authoritative.

Combat may continue while a participant is at 0 HP.

Initiative remains intact.

==================================================
28. DEAD PARTICIPANTS
==================================================

Do not invent new death mechanics.

If the authoritative Death System declares a participant Dead and
removes them from active Combat participation:

Initiative must handle that removal safely.

Do not automatically reroll everyone else's Initiative.

Do not reorder the remaining participants unnecessarily.

Do not alter completed Initiative results.

The exact death-resolution behavior remains owned by #08.

==================================================
29. ADDING NEW COMBATANTS
==================================================

A new creature can enter an already-running Combat encounter.

When an authoritative new combatant joins:

- roll Initiative for the newcomer
- do not reroll existing combatants
- insert the newcomer into the existing Initiative order.

Do not restart Combat.

Do not reset the round.

Do not reroll existing Initiative values.

Do not move existing participants simply because a new participant joined.

If multiple new combatants join together, apply the appropriate
authoritative grouping rules.

==================================================
30. NEW COMBATANT INSERTION
==================================================

The insertion must preserve:

- existing Initiative totals
- existing order
- current round
- current actor
- current turn progress.

If the new combatant's Initiative places it later in the current
round, it may receive its turn at that position.

If its position is before the current turn position, do NOT
retroactively replay already completed turns.

Use a deterministic current-round insertion policy and document it.

Do NOT silently restart the round.

==================================================
31. REMOVING COMBATANTS
==================================================

When a participant legitimately leaves Combat:

- remove only that participant from Initiative order
- preserve everyone else's Initiative totals
- preserve the current round
- preserve the current actor where possible
- advance safely if the removed participant was the current actor.

Do not reroll Initiative.

Do not reconstruct the order from current modifiers.

Make removal idempotent.

==================================================
32. SAVE / RESUME
==================================================

The following Initiative state must survive save/resume:

- Initiative order
- Initiative totals
- Initiative modifiers/result context where needed
- round number
- current turn index
- current actor
- participant membership
- group Initiative assignments
- relevant Initiative effects
- any pending Initiative-related state.

Example:

Round 3
Order:
Player → Goblin A → Goblin B → Orc

Current actor:
Goblin A

Save.

Resume.

The system must continue from exactly that canonical position.

Do NOT reroll Initiative on load.

==================================================
33. PERSISTENCE
==================================================

Initiative initialization and turn transitions must use the existing
persistence architecture.

Do NOT create:

- separate Initiative database
- separate Initiative save file
- separate Initiative persistence layer.

Persist through the existing authoritative Combat state.

==================================================
34. IDEMPOTENCY
==================================================

Repeated requests must not corrupt Initiative.

Examples:

- retry the same turn request
- retry after network timeout
- browser refresh
- duplicate API request
- repeated turn-end request
- repeated Combat-start request

must not:

- reroll Initiative
- duplicate participants
- duplicate Initiative entries
- advance two turns
- increment round twice
- consume RNG twice.

Use the existing receipt/idempotency mechanism.

Do not create a parallel receipt system.

==================================================
35. ROLLBACK / RNG PRESERVATION
==================================================

Preserve the existing rollback architecture.

Rollback must not silently introduce:

- a different Initiative roll
- duplicated RNG consumption
- lost action receipts
- duplicated turn transitions.

Existing AI-DND rollback rules remain authoritative.

Do not redesign rollback here.

==================================================
36. INITIATIVE AND CAMPAIGN TIME
==================================================

Initiative itself does NOT advance Campaign Time.

The existing #01 Campaign Time rule governs combat time advancement.

A completed combat round may advance Campaign Time according to #01.

Do not add extra seconds because:

- Initiative was rolled
- a turn started
- a turn ended
- Initiative order changed.

Do not create a second combat-time clock.

Do not create a new Initiative encounter.

40. PLAYER AGENCY
==================================================

Initiative determines WHEN a creature can act.

It does not decide WHAT the player chooses to do.

Do not introduce forced player decisions.

The player may still choose among all legal options available during
their turn.

Natural language remains supported.

Examples:

"Önce gobline saldırıyorum."

"Kapıya doğru koşuyorum."

"Bekliyorum."

"Ready alıyorum."

These are passed to the appropriate authoritative Action Economy /
Combat systems.

Initiative only establishes the actor's turn.

==================================================

- secretly reorder Initiative
- give the player an extra turn

through the Reaction/Ready rules from #04.
