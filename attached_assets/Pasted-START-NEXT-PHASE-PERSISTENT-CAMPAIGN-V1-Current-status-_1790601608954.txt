==================================================
PRIMARY GOAL
==================================================

Implement reliable persistent campaign save/load so a player can:

1. Start a campaign
2. Play normally
3. Save automatically and/or explicitly
4. Close the browser
5. Restart the server
6. Return later
7. Continue the SAME campaign
8. Recover the SAME canonical Python state

This must preserve:

- character
- HP / max HP
- AC
- stats
- inventory
- equipment
- location
- NPCs
- NPC memory
- world state
- combat state
- story/message history where already supported
- session metadata required for safe continuation

The canonical state must remain Python-owned.

==================================================
PHASE 1 — DEFINE PERSISTENT CAMPAIGN MODEL
==================================================

Create a server-side persistent campaign registry.

A campaign needs at minimum:

- campaign_id
- display_name
- created_at
- updated_at
- last_played_at
- save_version
- engine_version/hash metadata
- canonical serialized GameSession state
- safe campaign metadata for listing

Use UUID4 or similarly opaque identifiers.

Do not expose Python object ids.

Do not use predictable sequential IDs.

==================================================
STORAGE CHOICE
==================================================

For Persistent Campaign V1:

Prefer the simplest robust server-side persistence.

Use either:

A. Existing engine save files if already sufficient
or
B. A small SQLite-backed campaign registry plus engine save payload

Do NOT introduce:
- Redis
- external database
- distributed storage
- cloud object storage

unless the current project already requires it.

The goal is reliable single-instance persistence first.

==================================================
FILE / DATABASE SAFETY
==================================================

Persistence must be safe against:

- partial writes
- corrupted files
- interrupted server shutdown
- invalid JSON
- incompatible versions
- missing campaign files
- duplicate IDs

If using files:
- write atomically
- fsync/replace safely where practical
- keep validation before commit

If using SQLite:
- use transactions
- validate payload before commit

Do not overwrite the only known-good save with an invalid state.

Add or extend FastAPI endpoints.

--------------------------------------------------

POST /api/campaigns

Creates a persistent campaign.

If character creation is not yet canonical, allow creation from a new server-side
GameSession using current supported defaults.

Do not fake unsupported character creation behavior.

Return:
- campaign_id
- session_id
- canonical state

--------------------------------------------------

GET /api/campaigns/{campaign_id}

Returns safe campaign metadata + current canonical UI state.

--------------------------------------------------

POST /api/campaigns/{campaign_id}/resume

Loads/reconstructs a fresh runtime GameSession from persistent storage.

Return:
- new/current session_id
- campaign_id
- canonical state

--------------------------------------------------

POST /api/campaigns/{campaign_id}/save

Persist the CURRENT server-side GameSession.

Frontend must NOT submit canonical state.

The request may contain nothing, or only safe metadata like display name.

The server must serialize its own authoritative session state.

--------------------------------------------------

DELETE /api/campaigns/{campaign_id}

Optional for V1 if implemented safely.

If implemented:
- require explicit user action
- delete only that campaign
- do not expose filesystem paths

==================================================
AUTO-SAVE
==================================================

Implement server-side autosave.

Recommended behavior:

- after every successful authoritative turn
OR
- after every N seconds / turn completion

Prefer saving AFTER a completed successful turn.

Do not save:
- half-processed state
- failed engine turn
- partially mutated state

If a turn fails:
- previous valid save remains available

==================================================
SESSION VS CAMPAIGN
==================================================

Keep these concepts separate:

SESSION:
temporary live runtime GameSession in memory

CAMPAIGN:
persistent saved adventure

A resumed campaign may receive a new session_id.

campaign_id must remain stable.

Example:

campaign_id = permanent identity
session_id = current in-memory runtime identity

Do not confuse them.
