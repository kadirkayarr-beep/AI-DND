==================================================
4. STRICT PRE-#3 BLOCKER STANDARD
==================================================

A task may be classified PRE-#3 BLOCKER only when concrete evidence supports at least one of the following:

1. A reproducible current-code failure.

2. A demonstrated production defect, such as:
   - authoritative test failure,
   - release-gate failure,
   - direct reproducible probe,
   - import/parse/discovery failure,
   - broken runtime/API/persistence behavior.

3. A completed production-changing task whose critical behavior has not yet been verified on the current exact HEAD.

4. A genuinely uncovered ownership boundary involving:
   - canonical Python state,
   - session/campaign isolation,
   - persistence/rollback,
   - save compatibility/migration,
   - idempotency/action receipts,
   - Campaign Time,
   - combat/death/action economy,
   - model-call budget,
   - deterministic narration fallback,
   - API/runtime/client contract.

5. A real release-gate blind spot capable of allowing one of these contracts to regress undetected.

6. A concrete runtime/OpenAPI/generated-client mismatch affecting supported behavior.

7. A current syntax/import/discovery/tooling defect that prevents authoritative verification from running.

==================================================
5. WHAT DOES NOT JUSTIFY BLOCKING PACKAGE #3
==================================================

Do NOT make a task PRE-#3 BLOCKER merely because the exact combination has never been tested.

Normally NON-BLOCKING:

- another malformed type for an already-established fail-closed rule,
- another species using the same proven owner,
- another natural-language wording of the same proven intent contract,
- another actor pairing for an already-sufficiently-tested symmetric owner,
- another replay permutation of the same receipt contract,
- another save/reopen combination of an already-proven invariant,
- another endpoint using the exact same validated owner and error boundary,
- another contract-parity mutation handled by the same proven structural checker,
- another resource type following an already-proven persistence owner,
- another concurrency permutation without a new ownership boundary.

“Not an exact duplicate” is NOT enough.

Ask instead:

Does this expose a materially new authority, persistence, isolation, compatibility or release-readiness risk?
