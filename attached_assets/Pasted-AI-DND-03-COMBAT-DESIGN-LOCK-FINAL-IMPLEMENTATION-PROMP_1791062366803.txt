AI-DND — #03 COMBAT DESIGN LOCK
FINAL IMPLEMENTATION PROMPT

IMPORTANT:

#01 Campaign Time V1 is complete.
#02 Campaign Time Edge Cases is complete and verified.

Current Combat implementation already exists and must be audited before modification.

This task is NOT a combat rewrite.

The goal is to lock and harden the authoritative Combat lifecycle while preserving:
- Python game authority
- existing Combat ownership
- existing Campaign Time behavior
- existing Death System
- existing persistence
- existing action receipt/idempotency
- maximum 2 model calls per turn
- session isolation
- #02 event → combat handoff behavior
- player freedom

Do not silently redesign adjacent systems.

==================================================
1. AUTHORITY
==================================================

Python is the sole authority for Combat reality.

Python decides:
- whether Combat is active
- who participates
- combat ID
- participant state
- round
- turn
- current actor
- legal combat state transitions
- combat termination
- combat results
- HP/state changes
- persistence
- replay/idempotency

Qwen:
- interprets player intent,
- receives verified Combat context,
- narrates verified results.

Qwen must NOT:
- decide whether Combat starts
- decide initiative
- decide whether an action is legal
- decide hit/miss
- decide damage
- decide death
- decide combat termination
- mutate Combat state.

Frontend:
- presents authoritative Combat state,
- sends player intent,
- never creates Combat truth.

==================================================
2. SCOPE BOUNDARY
==================================================

THIS TASK DEFINES COMBAT LIFECYCLE ONLY.

Do NOT implement or redesign:

- Action Economy (#04)

but their detailed rules belong to their own locks.

If an existing Combat path already depends on one of these systems,
preserve the existing contract unless this prompt explicitly requires
a lifecycle fix.

==================================================
3. COMBAT START
==================================================

Combat starts only when Python determines that a real hostile combat
encounter has been established.

The following do NOT automatically start Combat:

- hostile attitude
- threat
- argument
- negotiation
- intimidation
- observation
- hostile encounter merely being generated by Campaign Time
- Qwen deciding that "combat feels appropriate"

#02 behavior must remain:

Hostile encounter
↓
player/world interaction
↓
player decision or authoritative combat trigger
↓
Combat starts

Do not allow Qwen or frontend to directly call Combat-start semantics
through prose.

When Combat starts, Python creates/records an authoritative combat state.

==================================================
4. COMBAT ID
==================================================

Every active Combat must have a stable authoritative Combat ID.

The Combat ID must remain stable across:
- turns
- rounds
- save/resume
- retry
- API responses

Do not create a new Combat ID because of:
- frontend retry
- narration retry
- page refresh
- save/load
- repeated identical action request.

==================================================
5. PARTICIPANT INTEGRITY
==================================================

Every Combat participant must have an authoritative identity.

The Combat state must distinguish:

- participant
- current actor
- valid target
- defeated participant
- inactive participant

The current actor must always belong to the active Combat.

A target must be validated against current Combat state.

Never resolve an attack or combat action against:
- an unrelated NPC
- an arbitrary session entity
- a stale participant ID
- an entity no longer present in the Combat
- a target selected only by Qwen/frontend.

Combat participant state must remain internally consistent.

==================================================
6. COMBAT STATE MACHINE
==================================================

Combat must have explicit authoritative lifecycle states.

Existing names may be preserved.

Conceptually:

CREATED
↓
ACTIVE
↓
TURN_IN_PROGRESS
↓
TURN_RESOLVED
↓
NEXT_TURN / NEXT_ROUND
↓
ACTIVE
↓
COMBAT_END
↓
CLOSED

The implementation may use a different internal representation,
but the transitions must be deterministic and validated.

Invalid transitions must be rejected.

Do not silently repair an invalid Combat state by inventing game results.

==================================================
7. CURRENT ACTOR
==================================================

At any moment there must be exactly one authoritative current actor
when Combat is actively processing turns.

The current actor must come from the authoritative Combat turn order.

Do NOT determine the current actor from:
- the latest player message
- frontend selection
- Qwen narration
- arbitrary participant ordering.

If the current actor becomes unable to act because of an authoritative
state change, Combat must apply the appropriate existing rules/state
handling rather than silently selecting another actor.

Detailed incapacitation/death rules remain in #08 where applicable.

==================================================
8. TURN LIFECYCLE
==================================================

A turn follows this authoritative conceptual sequence:

CURRENT ACTOR
↓
VALIDATE CURRENT STATE
↓
ACCEPT INTENT / AUTOMATIC TURN RESOLUTION
↓
VALIDATE REQUEST
↓
RESOLVE ACTION THROUGH APPROPRIATE SYSTEM
↓
APPLY VERIFIED STATE CHANGES
↓
CREATE RESULT
↓
PERSIST RESULT / RECEIPT
↓
END TURN
↓
SELECT NEXT ACTOR

Do not allow narration to skip or reorder these phases.

Action Economy details belong to #04.

Initiative ordering details belong to #05.

Attack mechanics belong to #06.

==================================================
9. INVALID COMBAT REQUESTS
==================================================

A request that is not legal in the current Combat state must be rejected
before it mutates Combat state.

Examples:

- wrong actor
- invalid target
- target not in Combat
- Combat already ended
- stale Combat ID
- action incompatible with current state
- malformed request
- request from another session
- request using a stale turn.

Invalid requests must NOT:
- consume action resources
- roll combat dice
- deal damage
- advance Combat
- advance Campaign Time
- create a combat result
- create a false journal event.

Existing API error semantics should be preserved where possible.

==================================================
10. VALID RESOLUTION
==================================================

Once a valid Combat request is accepted:

Python resolves it through the authoritative existing resolution
layer/system.

Do not duplicate Core Resolution logic inside Combat.

Combat may orchestrate resolution, but it must not become a second
dice/mechanics authority.

Conceptually:

Combat
↓
Core Resolution / appropriate authoritative mechanic
↓
verified result
↓
Combat state mutation

==================================================
11. STRUCTURED COMBAT RESULT
==================================================

Every resolved Combat interaction must produce a structured,
authoritative result sufficient for:
- persistence
- replay
- UI presentation
- narration validation
- debugging/audit.

Use the existing result contract if one already exists.

Do NOT create a duplicate parallel result architecture.

The verified result should expose, where applicable:

- combat ID
- actor
- target
- action/result type
- roll/result information
- hit/miss/critical result where applicable
- damage/result where applicable
- HP before/after where applicable
- conditions/state changes where applicable
- defeated/downed state where applicable
- combat status
- next turn/current actor

Only fields actually resolved by the authoritative system should exist.

Do not fabricate values merely for narration.

==================================================
12. NARRATION BOUNDARY
==================================================

The authoritative flow is:

PLAYER INTENT
↓
PYTHON VALIDATION
↓
PYTHON RESOLUTION
↓
STRUCTURED VERIFIED RESULT
↓
QWEN NARRATION
↓
NARRATION VALIDATION
↓
PLAYER

Qwen may describe:
- what happened
- what the player sees
- sensory details
- combat atmosphere
- consequences already present in verified state.

Qwen may NOT:
- add damage
- add enemies
- kill a participant
- change HP
- create a hit/miss
- create a critical
- create a new condition
- end Combat
- start Combat
- change position
- change inventory.

Rejected narration must use the existing deterministic fallback.
Do NOT add a model retry.

Maximum 2 model calls per turn remains unchanged.

==================================================
13. ZERO HP DOES NOT AUTOMATICALLY END COMBAT
==================================================

A player reaching 0 HP must NOT by itself call combat termination.

The existing Death System owns:
- Unconscious
- Death Saves
- Stable
- Dead
- recovery/death behavior.

Combat must remain active when appropriate.

Do NOT duplicate Death System logic inside Combat.

Combat must correctly observe authoritative Death state.

If all combatants capable of continuing the conflict are gone,
Combat may terminate according to the authoritative combat-end rules.

==================================================
14. COMBAT TERMINATION
==================================================

Combat ends only when the authoritative combat condition has ended.

Examples may include:

- hostile opponents defeated
- opponents flee
- opponents surrender
- sides cease hostile engagement
- authoritative encounter result ends the conflict.

Do NOT end Combat merely because:

- player reaches 0 HP
- player skips a turn
- player has no preferred action
- Qwen narrates an ending
- frontend closes/reloads
- a request fails
- one attack misses.

Combat termination must be deterministic.

==================================================
15. COMBAT END STATE
==================================================

When Combat ends:

- active Combat must be marked closed/inactive
- transient turn processing must stop
- no future Combat turn may execute against it
- stale requests must be rejected
- Combat ID remains available for historical/result references
- canonical outcomes remain persisted.

Do not delete historical combat results merely because active Combat ended.

==================================================
16. COMBAT → CAMPAIGN TIME
==================================================

Preserve #01 Campaign Time behavior.

A completed Combat round represents approximately 6 seconds.

The existing Campaign Time implementation is authoritative.

Combat must NOT create an additional arbitrary time jump when Combat ends.

Do NOT add:
- +10 minutes after Combat
- automatic rest time
- travel time
- arbitrary recovery time.

If Campaign Time is advanced by completed rounds,
use the existing #01 mechanism.

Do not create a second clock.

==================================================
17. COMBAT + CAMPAIGN EVENT HANDOFF
==================================================

Preserve #02 behavior.

A Campaign Time event may create a hostile encounter.

However:

EVENT
↓
HOSTILE ENCOUNTER
↓
PLAYER / AUTHORITATIVE COMBAT DECISION
↓
COMBAT

is the allowed handoff.

Combat does NOT automatically resume the interrupted previous task
after it ends.

After Combat ends, a new player decision may be required.

Do not automatically:
- resume travel
- resume research
- resume rest
- continue a previous action
without an authoritative rule allowing it.

Existing task/travel progress from #02 must not be lost.

==================================================
18. COMBAT + LOCATION
==================================================

Active Combat and participant location/context must remain consistent.

A participant cannot:
- start travel while remaining in an active Combat
- teleport to an unrelated location through a normal travel action
- leave Combat through frontend-only state changes
- remain in Combat after an authoritative relocation that ends the encounter.

Do not invent a complete spatial combat engine in this task.

Use the existing authoritative location model.

Detailed movement/position mechanics belong to later Combat locks.

==================================================
19. SAVE / RESUME
==================================================

Active Combat must survive save/resume.

Save must preserve enough authoritative state to resume exactly:

- Combat ID
- participants
- current round
- current turn
- current actor
- relevant combat state
- relevant HP/state
- required result/history state
- action receipts.

Resume must NOT:
- reroll initiative
- create a new Combat
- replay a resolved turn
- advance Campaign Time again
- reroll a previous combat action.

==================================================
20. RETRY / IDEMPOTENCY
==================================================

Combat actions must use the existing action receipt/idempotency mechanism.

If:

action_id = ABC

was successfully resolved:

Retry:

action_id = ABC

must return the existing result.

It must NOT:
- attack again
- roll again
- deal damage again
- advance the turn twice
- advance Campaign Time twice
- create duplicate history.

If the same action ID is reused for a materially different request,
preserve the existing conflict/409 behavior.

Do not create a second idempotency system.

==================================================
21. SESSION ISOLATION
==================================================

Combat state must remain isolated per campaign/session.

Player A must never:
- see Player B's Combat
- target Player B's participant
- reuse Player B's Combat ID
- resolve Player B's turn.

Session/campaign identifiers must be authoritative.

Do not rely on frontend filtering for isolation.

==================================================
22. REJECTED / FAILED RESOLUTION
==================================================

Distinguish:

INVALID REQUEST
vs
VALID ACTION THAT RESOLVES TO FAILURE.

Example:

"No weapon available for this requested weapon action"

may be invalid.

A valid attack that rolls and misses is NOT an invalid request.

This distinction is essential for:
- resource consumption (#04)
- receipts
- narration
- combat history.

Do not solve Action Economy here;
preserve the boundary so #04 can attach to it.

==================================================
23. ROUND BOUNDARY
==================================================

A round completes only after the authoritative turn sequence reaches
the end of the current round.

Do not increment the round:
- when a player submits an intent
- after one participant acts
- after a single attack
- because frontend refreshed
- because a request was retried.

When a round genuinely completes:
- existing round state advances
- Campaign Time receives the existing +6-second progression
- next round begins only if Combat remains active.

Do not create a second time advancement path.

==================================================
24. NO HIDDEN AUTO-TURNS
==================================================

Do not silently invent turns for:
- dead participants
- participants not in Combat
- arbitrary NPCs
- stale participants
- frontend-selected entities.

If an NPC/monster automatic turn already exists,
it must operate only for authoritative participants in the current
Combat.

Monster-specific behavior remains #07.

==================================================
25. COMBAT HISTORY
==================================================

Combat results that are canonical should remain available after Combat ends.

History may contain:
- combat started
- authoritative turns/results
- combat ended
- relevant canonical consequences.

Do not turn every narration sentence into a canonical Combat event.

Narration is not history authority.

==================================================
26. ERROR SAFETY
==================================================

If persistence fails while resolving a Combat action:

Do NOT report success.

Do NOT tell Qwen that the action happened.

Do NOT return a successful combat result if the authoritative state
was not safely persisted.

Use the existing transaction/rollback behavior.

Do not invent a new persistence architecture.
