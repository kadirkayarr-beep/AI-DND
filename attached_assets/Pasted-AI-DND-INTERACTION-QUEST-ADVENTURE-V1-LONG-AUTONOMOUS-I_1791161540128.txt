AI-DND — INTERACTION & QUEST ADVENTURE V1
LONG AUTONOMOUS IMPLEMENTATION PASS

You are beginning the first major AI-DND V2 gameplay package:

INTERACTION & QUEST ADVENTURE V1

This is intentionally a large, important package.

The goal is NOT to build a conventional quest-log system or a menu-driven dialogue system.

The goal is to make the player feel that they inhabit a persistent Forgotten Realms world where they can attempt natural, open-ended actions, negotiate, investigate, make plans, create their own goals, betray expectations, change sides, discover hidden truths, and cause persistent consequences.

The player must not feel like they are talking to an AI chatbot.

============================================================
MODEL CALL CONTRACT
============================================================

Maximum 2 model calls per player turn.

Preferred pattern where needed:

1. optional intent / structured proposal call
2. Python validation + authoritative resolution
3. optional narration call

Many turns may use zero or one model call.

No model retry loops.

If intent/proposal output is invalid:
fail closed or use deterministic fallback.

If narration is rejected:
use deterministic immersive fallback.
DO NOT call Qwen again.

Do not add a third call for:
- novelty checking
- quest generation
- NPC decision checking
- safety validation
- rewriting rejected narration

If multiple creative candidates are needed, request multiple bounded proposals
inside ONE permitted proposal call and let Python validate/select.

============================================================
PACKAGE PHILOSOPHY
============================================================

PLAYER FREEDOM IS OPEN-ENDED, NOT MENU-BOUNDED.

The player should not be restricted to predefined choices like:

A) Accept
B) Decline
C) Ask for more gold

The player may instead say:

"I don't want the gold. Give me the sword you're carrying."

"I don't trust you. I'm leaving."

"I'll help you, but first tell me what you're hiding."

"I want to work with the bandits instead."

"I think the mayor is corrupt. I want to investigate him."

"I wait until the guard shift changes, enter through the back alley,
find the records room, and if caught I pretend to work for the merchant."

The system should attempt to understand and resolve such intentions through
general contracts rather than thousands of hardcoded phrase branches.

CORE CONTRACT A — OPEN-ENDED PLAYER AGENCY
============================================================

Implement or harden the architecture required for natural open-ended player actions.

At minimum support the design needed for:

- natural interaction
- open-ended negotiation
- bargaining
- reward counter-offers
- refusal
- delay
- conditional agreement
- threats
- promises
- requests for information
- requests for services
- requests for items
- changing sides
- abandoning a plan
- betraying a quest giver
- helping an unexpected faction
- player-created goals
- off-script problem solving

Do NOT special-case every sentence.

Prefer a generic structured intent/action/proposal contract consistent with
existing architecture.

Example:

NPC offers 100 GP.

Player:
"I don't care about the gold. Give me your sword."

The engine should be able to represent:

intent = negotiate / counter_offer
requested consideration = existing canonical sword
rejected consideration = 100 GP

Python must validate:
- NPC exists
- sword exists
- NPC owns it
- transfer is possible
- item is not mechanically/lore locked
- proposed exchange does not violate canonical state

NPC willingness may use bounded Qwen agency based on verified context,

Do NOT implement the full Equipment/Loot/Economy V1 package here.

Use existing inventory/equipment capabilities only where already available.
Create clean interfaces for later package expansion instead of prematurely
building the economy package.

- witnessed facts

- know

- lie

- misunderstand
- repeat rumors
- manipulate

- ask for something in return

- goals
- fears

- relationships
- leverage
- debts
- promises

But Qwen does not directly alter state.

============================================================
CORE CONTRACT C — IMMERSIVE UNCERTAINTY / NO CHATBOT LANGUAGE
============================================================

This is HIGH PRIORITY.

The player-facing game must not say things such as:

"I don't have information about that."
"I cannot answer that."
"I don't have access to that data."
"This action is unsupported."
"I cannot perform this command."
"The backend cannot..."
"The model doesn't know..."
"Python..."
"server..."
"canonical record..."

Unknown, impossible, unavailable, unsupported, or uncertain situations
must be expressed DIEGETICALLY.

Examples:

Bad:
"I don't have information about Thay."

Good:
"Thay? Wrong person to ask. A caravan from the east passed through last tenday;
they might know more."

Bad:
"This action is unsupported."

Good:
"The stone door refuses to move, no matter how you brace yourself against it."

Bad narrator:
"There is insufficient data to answer."

Good narrator:
"Nothing you have learned so far confirms that claim."

Create or harden validation for:
- meta-AI language
- developer/backend terminology
- data-access language
- unsupported certainty
- out-of-world refusal wording

Rejected narration must use deterministic immersive fallback.
NO model retry.

NPC ignorance is allowed.
META ignorance is not.

============================================================
CORE CONTRACT D — SOCIAL RESOLUTION
============================================================

Social interaction must not become:

roll Persuasion -> mind control.

Where mechanical checks are appropriate, use verified 2024 rules and existing
Python-owned check resolution.

Not every conversation needs a roll.

"What's your name?"
usually needs no Persuasion check.

Social resolution may consider verified context such as:
- NPC goals
- leverage
- relationship
- fear
- evidence
- promises
- bribes/offers
- risks
- existing loyalties
- player reputation where already available
- relevant skill check where rules call for one

A high roll cannot make an impossible request automatically succeed.

Preserve player agency AND NPC agency.

Support partial success / success with complication where legitimate,
but the canonical consequence must still be Python-owned.

============================================================

Do not build a simplistic MMORPG quest box.

The internal system may still expose structured state, but conceptually treat

Potential lifecycle may include, where appropriate:

latent
discovered
offered
accepted
active
progressing
reframed
succeeded
failed
abandoned
expired

Do not force every thread through every state.

Support:
- explicit quests
- implicit adventure threads
- player-created goals
- optional objectives
- hidden facts/objectives
- branching paths
- objective reframing
- side switching
- betrayal
- refusal
- abandonment
- failure
- time-sensitive developments
- consequences that outlive the quest

A quest is not just:

go there -> kill X -> return -> reward

A completed or failed adventure may generate campaign events such as:
- NPC survived/died
- NPC opinion changed
- local rumor changed
- promise fulfilled/broken
- another opportunity opened
- a faction became aware
- a later callback became possible

Only create consequences justified by the resolved outcome.

Do not silently implement full Reputation/Factions/Living World V1.
Where later packages own deeper behavior, create narrow integration points.

============================================================
CORE CONTRACT F — MULTIPLE WAYS TO PROGRESS
============================================================

Avoid hardcoded single-solution adventures.

Where reasonable, the player should be able to:
- negotiate
- investigate
- sneak
- deceive
- bribe
- threaten
- ask another NPC
- use evidence
- side with the opposition
- leave
- return later
- fail and discover another route

The engine must not require the exact authored path if the player's alternative
is mechanically and fictionally legitimate.

No-dead-end policy:

A missed clue should not automatically make the entire campaign impossible.

But do NOT make progress automatic either.

Alternative progression should come from plausible world state,
new evidence, consequences, other actors, investigation, or later opportunity.

============================================================
CORE CONTRACT G — PLANS, NOT ONLY SINGLE ACTIONS
============================================================

This is important.

The player may express a multi-step intention such as:

"After the guards change shift, I go through the back alley,
find the records room, and if someone catches me I claim I work
for the merchant."

Do not simply execute the entire plan invisibly.

Design a bounded plan/intention representation that can identify:

- goal
- stated steps
- preconditions
- dependencies
- interruption points
- likely checks
- conditions under which control must return to the player

The game must never make major unstated decisions on behalf of the player.

Safe/obvious plan continuation may proceed where existing rules allow,
but meaningful decisions, new risks, irreversible choices, or unexpected
situations should return control to the player.

Do not turn this into a separate planning AI loop.

Respect the 2-call budget.

Qwen may NOT:

============================================================

Create a bounded novelty mechanism so emergent adventure generation does not
collapse into endless variants of:

Track enough recent campaign-generation metadata to detect repetition, such as:

- recent themes
- recent conflict types
- recent NPC motivations
- recent objective structures
- recent locations
- recent antagonist types
- recent reward patterns
- recent resolution styles

Do NOT store raw Qwen prose as canonical novelty truth.

Prefer structured tags/categories owned by Python.

candidate proposals.

Python may reject repetitive/invalid candidates and choose another candidate
from the SAME call.

Do NOT retry the model if all candidates fail.

============================================================

- deadline expires
- NPC leaves

- rival actor acts first
- target escapes
- planned event happens
- opportunity closes
- another actor resolves part of the problem

Do NOT use wall-clock time.

Player absence should matter where appropriate,

============================================================

Do not assume every NPC knows every campaign event.

============================================================
CORE CONTRACT M — CONSEQUENCE ECHOES / CALLBACKS
============================================================

Campaign history should be capable of producing later callbacks.

Examples:
- a spared enemy returns later
- a person helped earlier recognizes the player
- a broken promise resurfaces
- a rumor from an old event reaches a new place
- an NPC asks about a previous unresolved matter

Do NOT force every event to return.

Callbacks should be selective and grounded in persisted campaign canon.

Qwen can narrate or propose callbacks,
but Python chooses eligible historical facts and validates the resulting event.

Create or design the smallest useful pacing layer necessary to prevent

- observation
- social opportunity

- quest/adventure seed
- complication
- discovery

- nothing notable

This layer must respect:

- novelty

- Campaign Time
