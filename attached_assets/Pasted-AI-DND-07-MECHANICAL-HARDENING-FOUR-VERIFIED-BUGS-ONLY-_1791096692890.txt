BUG #1 — LIMITED RESOURCE RESET
============================================================

Verified problem:

`monster_combat.py:28–57`

When the Combat ID changes, the actor's monster resource record can be
deleted and recreated with its initial number of uses.

Verified reproduction:

- one-use attack
- use it
- remaining uses = 0
- combat ends
- same NPC participates in another combat
- resource incorrectly becomes 1 again
- no Long Rest occurred.

This is incorrect.

REQUIRED BEHAVIOR:

A resource that is defined as limited-use and restored by a specific
authoritative recovery condition must NOT reset merely because:

- Combat ID changes
- combat ends
- a new combat begins
- the NPC leaves/re-enters combat
- initiative is rebuilt.

The resource must remain exhausted until its actual authoritative
recovery condition occurs.

If the existing resource model specifies Long Rest as the recovery
condition, only that existing Long Rest owner may restore it.

Do NOT invent a new resource system.

Do NOT create a second resource ledger.

Reuse the existing resource/persistence ownership.

IMPORTANT:

Do not globally change all monster resources without inspecting how
the existing implementation distinguishes:

- per-combat resources
- limited-use resources
- recharge resources
- rest-recovered resources
- other statblock-specific resources.

Only fix the incorrect reset behavior.

REGRESSION TEST:

Create a focused test:

initial:
uses = 1

use resource:
uses = 0

end combat

start another combat with same canonical actor

assert:
uses == 0

then perform the existing authoritative recovery condition

assert:
uses == 1

Also test that an unrelated Combat ID change does not consume RNG or
create duplicate receipts.

BUG #2 — MULTIATTACK EXHAUSTED COMPONENT
============================================================

Verified problem:

`monster_combat.py:227–230, 363–398`

A Multiattack can contain a component whose resource is already exhausted.

Verified reproduction:

- `claw.remaining = 0`
- Multiattack contains two claw slots
- resolver still produces two claw attacks.

This must not happen.

REQUIRED BEHAVIOR:

Every individual Multiattack component must independently pass the
existing authoritative legality/availability checks before being executed.

Conceptually:

Multiattack
→ component A
→ check legal + available
→ execute only if available

→ component B
→ check legal + available
→ execute only if available

An exhausted component must NOT be executed.

Do not simply reject the entire Multiattack unless the existing
statblock/action contract explicitly requires the whole action to fail.

The smallest correct behavior is:

- unavailable component is skipped/rejected according to the existing
  action contract
- available legal components may still execute where the statblock
  permits.

The resolver must correctly apply:

- limited uses
- recharge availability
- component-specific legality
- resource consumption.

Do not consume a resource twice.

Do not allow a negative resource count.

Do not create a second Multiattack engine.

REGRESSION TESTS:

At minimum:

A:
Multiattack has two available claw components

→ claw does not execute.

C:
one component available
one component exhausted

Verified reproduction:

- its Reaction is available

The current behavior effectively treats missing threat information as
safe.

That is incorrect.

CRITICAL RULE:

UNKNOWN INFORMATION MUST NOT BECOME PROOF OF SAFETY.

Do NOT invent:

- distance
- visibility
- geometry
- enemy position
- Opportunity Attack availability.

But also do NOT treat missing data as evidence that no Opportunity Attack
can exist.

FIRST inspect the existing route/OA contract and existing canonical data
owners.

The fix must use the smallest existing authoritative mechanism.

If all required information is available:
→ perform the normal Opportunity Attack legality check.

If required information is incomplete:
→ do NOT silently authorize the movement as "safe" by omission.

Use the existing authoritative movement/error/uncertainty behavior if one
already exists.

If no appropriate behavior exists, introduce only the smallest explicit
"insufficient evidence / movement cannot be safely validated" outcome
required by the existing Action Economy contract.

Do NOT build a new geometry or pathfinding engine.

Do NOT guess the missing enemy position.

Do NOT assume:

"not in route target list = cannot make Opportunity Attack."

Do NOT assume:

"distance_unknown = safe."

The movement resolver must remain conservative when the information
required to establish movement legality is missing.

REGRESSION TESTS:

missing from the route list.

D:
missing data must not be replaced with fabricated distance/visibility.

E:
existing valid routes continue to work.

existing player agency and movement semantics remain unchanged.

IMPORTANT:

Do not solve this by generating fake perception or fake geometry.
