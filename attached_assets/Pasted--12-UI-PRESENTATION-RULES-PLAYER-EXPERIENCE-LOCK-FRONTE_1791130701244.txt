============================================================
PRIMARY PRODUCT GOAL
============================================================

AI-DND must feel like a real persistent Forgotten Realms RPG.

It must NOT feel like:

- an AI chatbot with fantasy colors
- a developer dashboard
- an API client
- an engine diagnostic screen
- a technical prototype

The player should feel:

"I am inside a D&D campaign."

Not:

"I am interacting with a software system."

The existing architecture remains authoritative:

PYTHON DECIDES GAME REALITY.
LORE AUTHORITY DECIDES SETTING REALITY.
CAMPAIGN EVENTS CREATE CAMPAIGN CANON.
QWEN UNDERSTANDS INTENT, USES VERIFIED CONTEXT, AND TELLS THE STORY.
FRONTEND PRESENTS REALITY.

============================================================
PRIMARY FRONTEND BASELINE
============================================================

Use:

artifacts/ai-dnd-experience

as the primary UI baseline.

Do not replace it with:

artifacts/ai-dnd-web

unless a specific compatibility reason is proven.

Existing useful foundations include:

- campaign library
- character creation

- character/inventory area
- narrative/transcript area
- World/NPC/Journal/Combat panels
- combat component separation
- responsive/mobile drawers
- environment-theme concept
- dark fantasy visual direction
- bronze accent language

Preserve good existing structure.

This is NOT permission for a total frontend rewrite.

============================================================
NON-NEGOTIABLE AUTHORITY RULE
============================================================

Frontend presentation may READ:

- canonical campaign metadata
- current location
- current time
- weather/environment metadata
- combat state
- HP
- conditions
- initiative
- action economy state
- spell resources
- inventory
- quests
- journal
- NPC data
- resolved skill/check results
- resolved combat results
- resolved narration

Frontend may transform these into presentation.

Frontend MUST NOT create:

- NPCs
- locations
- quests
- combat outcomes
- damage
- healing
- dice results
- campaign facts
- lore facts
- movement
- time advancement
- rewards
- inventory changes
- death outcomes
- spell outcomes

Atmosphere is presentation only.

A visual transition must never mutate canonical state.

============================================================
PLAYER-FACING LANGUAGE
============================================================

Remove technical implementation language from normal player-facing surfaces.

Normal gameplay must NOT expose:

- Python
- engine / motor
- backend
- server
- model
- Qwen
- canonical record
- receipt
- rollback implementation
- RNG
- database
- API
- request ID
- action ID

- local rendering
- debug terminology

These may remain available in:

- developer tools
- diagnostics
- internal debug panels
- development-only views

Do not simply delete useful diagnostics if they are already properly isolated.

Move technical information out of normal player experience where appropriate.

============================================================
CAMPAIGN DATE / LOCATION TRUTH
============================================================

Do NOT hardcode stale presentation values.

The current intended campaign-era baseline is:

1501 DR
Year of the Shining Mythal

The frontend must obtain date/year from canonical campaign/lore metadata.

Do NOT hardcode:

1492 DR

or other obsolete values as player-facing campaign truth.

Likewise do not hardcode generic values such as:

SWORD COAST

when the actual campaign metadata may instead specify:

The North
Neverwinter
or another canonical campaign location.

Presentation must render actual current campaign metadata.

============================================================
ENGINE HEALTH / TECHNICAL STATUS
============================================================

If the current player UI exposes an Engine Health or equivalent panel,
inspect it carefully.

Normal players should NOT see:

- backend availability
- engine name
- model name
- qwen3:8b
- internal API health
- implementation state

Move such information to:

Settings
Developer
Diagnostics

or another clearly non-player-facing surface.

If an internal service is unavailable, normal gameplay should receive a
player-friendly message.

Example style:

"Dungeon Master şu anda sessiz. Yeniden dene."

Do not expose internal stack details.

============================================================
CHARACTER CREATION
============================================================

Character creation should feel like creating a D&D character.

It must NOT feel like submitting parameters to a backend.

Remove or replace technical presentation such as:

- "motor kayıtlı seçimler"
- "Python zarlarıyla oluşturulacak"
- "kanonik Python kaydı"
- backend/server explanation
- implementation status text

Do NOT remove meaningful D&D information.

Keep useful:

- species/race
- class
- background
- abilities
- proficiencies
- equipment
- derived character information

If a portrait is unavailable:

DO NOT show technical missing-data warnings.

Use an intentional fantasy fallback such as:

- silhouette
- class emblem
- race/class heraldry
- engraved frame
- parchment illustration

Missing technical data must never visually announce prototype state.

============================================================
ADVENTURE SCREEN
============================================================

The Dungeon Master narrative should be the visual center.

Preferred hierarchy:

PRIMARY:
Dungeon Master narrative

SECONDARY:
player action

CONTEXTUAL:
mechanical roll/check/combat resolution

SUPPORTING:
character sheet
inventory
journal
nearby people
location details

The transcript should feel like:

an RPG campaign log

rather than:

a chat application.

Player actions may remain visually distinct.

They must not visually dominate the DM narrative.

NPC dialogue should be readable and clearly differentiated where appropriate.

============================================================
MECHANIC PRESENTATION
============================================================

Do not hide meaningful D&D mechanics.

Players should be able to understand important outcomes.

Examples:

GİZLENME

8 + 3 = 11

Başarısızlık

Sema’nın bakışları üzerinde kalıyor.

Mechanics should feel like part of the adventure.

Do not expose implementation wording around them.

Good:

"Başarısızlık — Sema'nın bakışları üzerinde kalıyor."

Bad:

"Python skill resolver returned failure."

============================================================
WORLD / CONTEXT PANELS
============================================================

The immediate adventure screen should prioritize the current scene.

Prefer contextual information:

- current location
- nearby people
- noteworthy objects/features
- active quest
- immediate combat context
- current relevant conditions

Avoid overwhelming the player with unrelated global information.

Full world/location lists belong more naturally in:

- Journal
- Map
- Codex

if those surfaces already exist.

Do NOT invent a new world simulation merely to populate UI.

============================================================
COMBAT PRESENTATION
============================================================

Combat should feel tense and readable.

When combat is active:

- foreground relevant combat information
- make current actor obvious
- make HP/state readable
- make action availability understandable
- make important rolls/results legible
- preserve initiative information where useful
- clearly distinguish player/NPC/monster states

Do NOT create mechanics in the combat UI.

Do NOT let visual state determine combat state.

Combat atmosphere may become more intense but should remain restrained.

Avoid:

- giant red overlays
- gaudy RGB
- excessive animations
- distracting screen effects
- arcade-style damage spam

Combat should feel dangerous, not flashy.

============================================================
DEATH PRESENTATION
============================================================

Use the actual #08 canonical state.

Player death state may visibly communicate meaningful:

- Unconscious
- Death Save
- Stable
- Dead
- recovery/relevant mode state

Do not hide mechanically important death information simply for immersion.

But do not expose internal implementation wording.

Bad:

"Death System checkpoint rollback pending."

Good:

"Ölümün eşiğindesin."

or a clear D&D-style death-save presentation consistent with the actual
canonical state.

NPC/monster death presentation must reflect canonical state.

Frontend must never infer death from animation alone.

============================================================
SPELL PRESENTATION
============================================================

Use ONLY the actual #09 supported spell scope.

Do not invent UI controls for deferred spells.

Spell UI must reflect:

- available spells
- actual resources
- actual action economy
- valid/invalid targets
- actual resolved result

Do not let a visually available spell imply that Python will accept it.

If a spell is unavailable, the UI must derive that from canonical state.

ACCESSIBILITY / READABILITY
============================================================

Do a practical accessibility pass without turning #12 into a separate
accessibility project.

- mobile text remains readable

Do not replace the visual identity with generic accessibility UI.

============================================================
UI STATE SAFETY
============================================================

Inspect frontend state handling.

Ensure:

- loading state cannot create fake canonical state
- failed API response does not invent success
- stale response does not overwrite newer canonical state
- deletion failure preserves the campaign card
- successful deletion removes the correct campaign
- replay/duplicate UI state does not imply duplicate gameplay
- frontend optimistic presentation does not become permanent truth

If frontend already correctly follows server state, preserve it.

Do not create a second client-side game state engine.

============================================================
TEST / VERIFICATION STRATEGY
============================================================

Before changing UI:

1. inventory existing frontend tests
2. inspect current UI components
3. identify genuine presentation gaps
4. make the smallest coherent frontend changes
5. do not rewrite already-good components

Expected changes should primarily be:

- React/TypeScript components
- styling/theme/presentation helpers
- player-facing copy
- UI tests
- documentation if necessary

Do NOT change Python gameplay code merely to support presentation.

If an API currently lacks a presentation field:

First determine whether the field already exists elsewhere.

Do not create a new gameplay state solely because the UI wants it.

If a genuinely missing canonical presentation field is discovered:

STOP and report it rather than inventing frontend truth.
