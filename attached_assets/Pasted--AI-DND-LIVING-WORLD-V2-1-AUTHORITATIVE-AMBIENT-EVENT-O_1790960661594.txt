# AI-DND — LIVING WORLD V2.1
# AUTHORITATIVE AMBIENT EVENT OUTCOME BOUNDARY
# ENGINEERING TASK

Living World V2 foundation has been completed and audited.

The audit established the following:

- Ambient events currently support GREEN atmospheric events and BLUE temporary scene references.
- Existing GameSession supports authoritative outcomes for normal player actions.
- Existing quest transitions have authoritative boundaries and idempotency.
- Limited Sword inventory transfer exists.
- NPC conversation memory exists.
- Persistence exists.
- However, there is currently NO dedicated authoritative boundary that accepts an ambient-event interaction, validates it, applies an allowed persistent result, rejects an invalid result, and prevents duplicate application of the same event instance.
- Ambient event selection/history is persisted, but event-result application is not.
- Narration/model output must never become state authority.

The purpose of this task is to create the smallest safe authoritative boundary required for future interactive ambient events.

THIS IS NOT A NEW WORLD SIMULATION.
THIS IS NOT A COMBAT REWRITE.
THIS IS NOT A QUEST REWRITE.
THIS IS NOT AN INVENTORY REWRITE.
THIS IS NOT A NEW AI GAME ENGINE.

The goal is a narrow engine-authoritative event-result transaction boundary.

============================================================
1. AUTHORITY RULE — NON-NEGOTIABLE
============================================================

Python/GameSession remains authoritative for:

- world state
- campaign state
- NPC state
- inventory
- quest state
- event state
- persistence
- canonical memory
- mechanical outcomes

Qwen remains:

- intent/context interpreter
- NPC/dialogue generator
- narrative generator

Qwen is NOT allowed to directly mutate:

- inventory
- gold
- quests
- NPC state
- world state
- event state
- campaign canon
- journal
- memory

A model-generated candidate may be passed to Python.

Python must validate it.

Only validated Python engine transitions may mutate canonical state.

============================================================
4. EVENT INSTANCE IDENTITY
============================================================

An ambient event definition ID is NOT sufficient.

We need a stable EVENT INSTANCE ID.

For example:

event definition:
street_dog_steals_meat

is not the same thing as:

event instance:
campaign-123 / location-456 / instance-789

The event instance must identify one concrete occurrence.

The same event definition may occur many times in a campaign.

But one event instance must only be able to produce its persistent outcome once.

Use existing ID conventions if possible.

Do not invent an incompatible second ID system if an existing stable event identity mechanism can be extended.

============================================================
5. IDEMPOTENCY KEY
============================================================

The event result must have a stable idempotency identity.

Conceptually:

(event_instance_id, player_action_id)

or an equivalent stable key.

The same action against the same event instance must not apply the persistent mutation twice.

Example:

Player interacts with an event.

First request:
APPLIED

Second identical request:
must NOT apply the mutation again.

It may return:

ALREADY_APPLIED
or an equivalent deterministic result.

Do not duplicate:

- items
- gold
- quest progress
- journal entries
- memory
- world state changes

============================================================
6. RESULT CONTRACT
============================================================

Create a small authoritative result contract.

At minimum the semantic result states must distinguish:

APPLIED
REJECTED
NO_EFFECT

If the existing architecture already has equivalent states, reuse them.

A result should contain enough information for the caller to understand the outcome without parsing narration.

Conceptually:

EventResult:
- event_instance_id
- action_id
- status
- reason/code
- applied transition identifier
- canonical event identifier
- optional safe result metadata

Do NOT put arbitrary narration into the authoritative result.

Narration is generated later.

NARRATION

============================================================
8. EVENT ELIGIBILITY
============================================================

Before applying a result verify:

- event instance exists
- event belongs to current campaign/session
- event is still active/eligible
- event has not already been resolved
- player is allowed to interact with it
- current location/context is compatible
- action is valid for that event
- any required preconditions are satisfied

If any condition fails:

REJECTED

No mutation.

============================================================
9. SESSION ISOLATION
============================================================

Campaign A must never be able to resolve:

Campaign B event instance.

Validate ownership:

campaign_id
session_id
character_id where relevant

before applying the result.

Test this explicitly.

============================================================
10. PERSISTENCE ATOMICITY
============================================================

The following logical operation must be treated as one authoritative transition:

1. validate event
2. apply allowed mutation
3. record canonical event result
4. persist updated state

Do not mark an event as applied before the actual mutation succeeds.

Do not persist the mutation without the canonical event result.

Do not create a canonical result for a rejected action.

Reuse the existing campaign/session persistence mechanism.

Do NOT invent a second persistence database.

If the existing persistence layer cannot safely guarantee this operation, stop and report the minimum missing capability instead of creating a hidden workaround.

============================================================
11. FAILURE SAFETY
============================================================

If validation fails:

NO STATE CHANGE.

If mutation fails:

NO PARTIAL CANONICAL EVENT.

If persistence fails:

do not claim success.

Do not return:

"Done!"

when the authoritative mutation did not persist.

The result must distinguish:

APPLIED
REJECTED
NO_EFFECT

and, where the existing architecture supports it, a deterministic internal failure state.

Never expose database/internal error jargon to the player.

============================================================

- inventory resolution
- quest resolution
- movement resolution

inside the ambient event system.

Ambient event system should orchestrate/contextualize.

GameSession/engine should resolve.

============================================================

ENGINE RESOLUTION
→ CANONICAL EVENT

============================================================
22. QWEN BOUNDARY
============================================================

Qwen may propose:

- player intent
- event interaction interpretation
- narration

Qwen may NOT decide:

- whether an event is eligible
- whether a mutation succeeds
- whether a quest is accepted
- whether an item was acquired
- whether gold changed
- whether an NPC died
- whether a world state changed

Python must decide.

If Qwen proposes an invalid action:

Python returns REJECTED or NO_EFFECT.

Narration explains the verified outcome.

============================================================
23. MAX MODEL CALL BUDGET
============================================================

MAX 2 QWEN CALLS PER TURN.

The event-result boundary itself must be deterministic and must not require a model call.

Do not add a retry loop.

Do not call Qwen to validate Python state.

Do not call Qwen to determine dice/check results.

============================================================
36. FINAL PRINCIPLE
============================================================

The Living World is not allowed to become a second game engine.

The ambient event system proposes CONTEXT.

The player provides INTENT.

Python validates and resolves.

The engine produces the canonical RESULT.

Persistence records it.

Memory can retrieve it later.

Qwen narrates the verified result.

The player experiences the consequence.

The architecture must remain:

PLAYER
→ INTENT
→ EVENT CONTEXT
→ PYTHON AUTHORITY
→ VERIFIED RESULT
→ PERSISTENCE
→ MEMORY
→ QWEN NARRATION

Never:

PLAYER
→ QWEN
→ "it happened"
→ WORLD STATE

And never:

AMBIENT EVENT
→ hidden mutation
→ fake canonical state.

Build the smallest real authoritative bridge.
Do not build a second engine.
