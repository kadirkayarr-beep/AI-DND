==================================================
2. PLAYER FREEDOM — EN ÖNEMLİ TASARIM KURALI
==================================================

Campaign Time oyuncunun özgürlüğünü kolaylaştıran yardımcı bir sistemdir.

Oyuncuyu gereksiz yere durdurmamalıdır.

Şu davranış KESİNLİKLE YASAK:

Player:
"15:00 → 20:00 boyunca seyahat ediyorum."

World event:
"18:00–18:30"

Sistem:
"18:12'de seni durdurdum."

YAPILMAYACAK.

Oyuncu event'i kaçırabilir.

World event yine canonical olarak gerçekleşebilir.

Oyuncu daha sonra aftermath'ı öğrenebilir.

Ancak event gerçekten oyuncunun bulunduğu yerde,
oyuncunun kararını gerektiren ve fiziksel olarak kaçınılmaz
bir interruption oluşturuyorsa action durabilir.

Oyuncunun yerine karar verilmez.

==================================================
3. EVENT LIFECYCLE
==================================================

Scheduled event'lerin mevcut sistemine uygun olarak gerekli lifecycle
ayrımını koru.

En azından kavramsal olarak şu durumlar birbirinden ayrılmalıdır:

- scheduled
- eligible / active window
- encountered
- pending player decision
- resolved
- missed / unseen
- expired

Mevcut model farklı isimler kullanıyorsa gereksiz rename yapma.

Ama aşağıdaki ayrımlar korunmalıdır:

EVENT OCCURRENCE != PLAYER ENCOUNTER
EVENT CANON != PLAYER KNOWLEDGE

Bir world event gerçekleşebilir,
ama oyuncu bunu hiç görmemiş olabilir.

==================================================
4. EVENT WINDOW
==================================================

Event window exact timestamp olmak zorunda değildir.

Örnek:

18:00–18:30

Bu:

"Event'in bu zaman aralığında encounter edilebilir /
gerçekleşebilir olduğu dönem"

anlamına gelir.

18:05:
player yetişebilir.

18:25:
player yetişebilir.

18:31:
event'in kendisi kaçırılmıştır.

Exact occurrence timestamp uydurma.

Event window tam Campaign Timestamp üzerinden değerlendirilmelidir.

Gece yarısı, ay veya yıl sınırlarını geçebilen event window'ları destekle.

==================================================
5. PLAYER ENTERS AN ACTIVE WINDOW
==================================================

Player event window içinde ilgili konuma/bağlama gelirse:

Python kontrol etmelidir:

- event hâlâ active mi?
- player location uygun mu?
- prerequisites geçerli mi?
- player event'i görebilir mi?
- event interaction gerektiriyor mu?
- event daha önce resolved mı?

Uygunsa event authoritative olarak resolve edilebilir.

Player event'i gördüğünde event otomatik olarak "başarılı"
sayılmamalıdır.

Event'in kendi canonical resolution sonucu uygulanmalıdır.

==================================================
6. EVENT WINDOW CLOSE
==================================================

Player event'i hiç görmediyse:

18:00–18:30
↓
18:30

event window kapanır.

World event canonical olarak gerçekleşmesi gerekiyorsa
world state'e uygulanır.

Player Knowledge'a otomatik olarak yazılmaz.

Player daha sonra aftermath üzerinden öğrenebilir.

Örnek:

Campaign Canon:
Caravan was ambushed.

Player Knowledge:
unknown.

Daha sonra player bölgeye geldiğinde:

- cesetler,
- kırılmış arabalar,
- NPC söylentileri,
- başka doğrulanmış aftermath

gibi sonuçlarla öğrenebilir.

Qwen kendi başına:
"Sen daha önce olan pusuyu biliyorsun."

diyemez.

==================================================
7. LONG ACTION + MULTIPLE EVENTS
==================================================

Player:

"15:00'te başlayıp 20:00'ye kadar seyahat ediyorum."

Campaign Time:

15:00 → 20:00

Arada:

16:00 Event A
17:15 Event B
18:00 Event C
19:20 Event D

olabilir.

Player action retroaktif olarak bölünmez.

Ancak Campaign Time ilerlemesi sırasında
world events authoritative olarak kronolojik biçimde değerlendirilir.

Event ordering:

1. dependency
2. explicit priority
3. location/causal relationship
4. deterministic tie-breaker

Random event ordering YASAKTIR.

Event A'nın sonucu Event B'nin prerequisite'lerini değiştirebilir.

Bu durumda Event B,
A'nın yeni world state'i üzerinden tekrar değerlendirilir.

==================================================
8. EVENT CHAINS
==================================================

Event'ler birbirlerinin sonucunu etkileyebilir.

Örnek:

Caravan ambushed
↓
Caravan destroyed
↓
Merchant does not arrive
↓
NPC meeting changes
↓
Later event changes

Bu davranış desteklenmelidir.

Ancak:

- infinite recursion
- circular event resolution
- duplicate resolution
- aynı event'in sonsuz yeniden tetiklenmesi

YASAKTIR.

Bir event aynı resolution context içinde
bir kez authoritative olarak resolve edilir.

Bir event başka bir event doğurursa,
yeni event canonical ID ile izlenir.

Causal dependency korunur.

Cycle tespit edilirse sistemi sonsuz döngüye sokma.
Yeni gerçeklik uydurma.
Mevcut canonical state'i koruyarak güvenli şekilde durdur
ve açık diagnostic/report üret.

Aynı event retry nedeniyle ikinci kez çözülmemelidir.

==================================================
9. SIMULTANEOUS EVENTS
==================================================

Aynı Campaign Timestamp veya aynı window içinde birden fazla event varsa:

Öncelik:

1. dependency
2. explicit priority
3. causal/location relationship
4. deterministic stable tie-breaker

Random ordering kullanılmayacaktır.

Birbirinden bağımsız iki event aynı zaman aralığında
gerçekleşebiliyorsa ikisi de canonical olarak gerçekleşebilir.

Player otomatik olarak yalnızca bir event'e zorlanmaz.

Player'ın bulunduğu yer ve event relevance belirleyicidir.

==================================================
10. INTERRUPTIBILITY
==================================================

Event'ler üç temel davranış gösterebilir:

A) NON-INTERRUPTIVE

Oyuncunun action'ını durdurmaz.

Örnek:
Şehrin başka tarafında kavga çıktı.

B) INTERRUPTIVE / AVOIDABLE

Player'ın karar verebileceği bir interaction oluşturur.

Örnek:
Yolda şüpheli bir grup player ile konuşmak istiyor.

Player:
- konuşabilir,
- devam edebilir,
- geri dönebilir,
- başka çözüm seçebilir.

Event otomatik combat başlatmaz.

C) FORCED / PHYSICALLY UNAVOIDABLE

Player action artık fiziksel olarak mümkün değildir.

Örnek:
Köprü tamamen çöktü.

Bu durumda action durabilir.

Player'a yeni karar sunulur.

ÖNEMLİ:

INTERRUPTIVE != AUTOMATIC COMBAT

INTERRUPTIVE != AUTOMATIC PLAYER DECISION

Python yalnızca objective game reality'yi belirler.

Player choice gerektiğinde player'a bırakılır.

==================================================
11. ACTION PROGRESS
==================================================

Bir action interruption noktasına kadar zaman tükettiyse
o süre kaybolmaz.

Örnek:

Requested:
60 dakika araştırma

Actual:
24 dakika

Event:
24. dakikada interruption

Sonuç:

elapsed = 24 min
remaining = 36 min

Bölünebilir task ise progress korunur.

Player devam etmek isterse
kalan süre/progress üzerinden devam eder.

24 dakika tekrar tüketilmez.

==================================================
12. EVENT → COMBAT
==================================================

Travel/event bir combat encounter oluşturabilir.

Ancak event yalnızca:

"hostile encounter oluştu"

gerçeğini yaratır.

Combat resolution:

- initiative
- attack
- damage
- death
- escape
- surrender

gibi konulara kendisi karar vermez.

Bunlar Combat sisteminin otoritesidir.

Combat bittikten sonra önceki action otomatik olarak
körlemesine devam etmez.

Player'a yeni decision point bırakılır.

==================================================
13. SAVE / RESUME
==================================================

Campaign Time,
event state,
pending player decision,
travel/task progress

aynı authoritative campaign persistence içinde korunmalıdır.

Save sonrası:

Campaign Time = 16:12
Event = pending
Progress = 1h12m

ise resume sonrası aynı state gelmelidir.

Resume:
- event'i tekrar roll etmez,
- occurrence zarını tekrar atmaz,
- type zarını tekrar atmaz,
- disposition zarını tekrar atmaz,
- zamanı tekrar ilerletmez.

==================================================
14. ATOMIC RESOLUTION
==================================================

Bir gameplay action'ın authoritative resolution zinciri:

Player Action
↓
Resolve action
↓
Advance Campaign Time
↓
Process applicable events
↓
Apply world consequences
↓
Update player knowledge if appropriate
↓
Create receipt
↓
Persist

aynı authoritative transaction sınırında korunmalıdır.

Yarım state oluşmamalıdır.

Örneğin şu durumlar oluşmamalıdır:

Campaign Time yeni
ama event eski.

Event yeni
ama world state eski.

World state yeni
ama receipt yok.

==================================================
15. RETRY / IDEMPOTENCY
==================================================

Aynı action tekrar gelirse:

SAME ACTION ID
↓
SAME RECEIPT
↓
SAME RESULT

olmalıdır.

Şunlar ikinci kez yapılmayacak:

- time advancement
- event roll
- event resolution
- world mutation
- task progress

Aynı ID farklı request ile kullanılırsa
mevcut 409/conflict davranışı korunacaktır.

Yeni bir idempotency architecture oluşturma.

Mevcut action receipt sistemini kullan.

==================================================
16. CRASH / RESTART
==================================================

Server kapanması Campaign Time'ı ilerletmez.

Oyuncu:

18:00

iken server kapandıysa:

resume:
18:00

olmalıdır.

Response kaybolduktan sonra request tekrar gelirse
receipt üzerinden önceki sonuç döndürülmelidir.

İkinci time advancement veya ikinci event resolution yapılmamalıdır.

==================================================
17. PENDING EVENT + SAVE
==================================================

Örnek:

16:12
↓
Ambush
↓
PENDING_PLAYER_DECISION
↓
SAVE

Resume:

16:12
↓
same pending encounter

olmalıdır.

Player karar vermeden event yeniden roll edilmez.

Event window'ın kapanması,
zaten active/pending encounter haline gelmiş event'i silmez.

==================================================
18. LONG TIME SKIP
==================================================

Player:

"Bir hafta boyunca burada kalıyorum."

derse:

Campaign Time:
+7 days

olabilir.

Bu durumda aradaki world events
chronological olarak authoritative şekilde değerlendirilir.

Ancak player'a yüzlerce event interaction'ı zorla gösterilmez.

Player ile ilgisiz event:
- world state'e uygulanabilir,
- player knowledge'a yazılmaz.

Player'ın bulunduğu ortamı doğrudan etkileyen
ve gerçek player decision gerektiren event:
- time skip'i o noktada durdurabilir,
- pending encounter oluşturabilir.

Player decision gerektirmeyen olaylar:
- time skip'i gereksiz yere bölmez.

==================================================
19. BULK TIME RESOLUTION
==================================================

Çok uzun skip'ler:

1 hafta
1 ay
vb.

için gerçek zamanın her dakikasını simüle etme.

Bulk chronological resolution kullanılabilir.

Ancak:

- event dependencies korunmalı,
- event ordering deterministic olmalı,
- player-decision gerektiren event'te bulk resolution durmalı,
- event resolution zamanı değiştirmemeli,
- aynı event tekrar çözülmemeli.

Travel Event Dice yalnız gerçek travel stage'lerinde çalışır.

"Bir hafta şehirde bekliyorum."

için yüzlerce travel event roll'u yapılmaz.

==================================================
20. TASK VS WAIT / TIME SKIP
==================================================

Bu ayrım korunmalıdır.

TASK:

"Bir saat araştırıyorum."

→ 1 saat maksimum/budget.

Task 6 dakikada tamamlandıysa:

+6 dakika.

WAIT / SLEEP / EXPLICIT TIME PASSING:

"3 saat bekliyorum."

→ +3 saat.

"Sabaha kadar uyuyorum."

→ Campaign Time üzerinden sabaha kadar gerçek süre.

Task ile explicit waiting aynı mekanizma gibi ele alınmamalıdır.
