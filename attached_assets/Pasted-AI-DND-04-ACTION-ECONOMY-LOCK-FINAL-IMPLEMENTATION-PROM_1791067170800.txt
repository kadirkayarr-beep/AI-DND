==================================================
1. SOURCE AUTHORITY
==================================================

Use the uploaded:

D&D 5e — Player's Handbook 2024

as the primary rules authority for Action Economy.

Python remains the sole authority that resolves actual gameplay.

The PHB informs the implementation.
Python determines the actual state.

Qwen:
- may understand player intent,
- may identify the likely intended action,
- may narrate verified outcomes.

Qwen must NOT:
- decide whether an action is legal,
- decide whether a resource is available,
- consume Action Economy resources,
- grant Action/Bonus Action/Reaction resources,
- create movement,
- decide whether Ready triggers,
- mutate canonical state.

Frontend:
- presents available resources,
- presents legal options returned by Python,
- sends intent,
- never decides Action Economy legality.

==================================================
2. CORE DESIGN PRINCIPLE
==================================================

Action Economy exists to represent what a creature can do during its
turn and in response to triggers.

It must support both:

A) structured UI actions
B) natural-language player actions

Both paths must reach the same authoritative Python validation/resolution.

Example:

UI:
[Attack]

and:

Player:
"I attack the goblin with my sword."

must resolve through the same authoritative action-economy validation.

Do NOT create separate mechanics for buttons and natural language.

==================================================
3. TURN RESOURCE MODEL
==================================================

At the beginning of a normal creature turn, Python must establish the
creature's available turn resources.

Conceptually:

TurnResources

- base_action
- additional_actions
- bonus_action
- reaction
- movement
- ready_state
- turn_state

Internal representation may differ.

Do NOT create a parallel combat state system.

The Action Economy state must belong to the authoritative active Combat
turn state.

==================================================
4. BASE ACTION
==================================================

A normal creature has one Action available on its turn.

However, do NOT hardcode:

"maximum one Action per turn"

as an absolute global restriction.

Certain rules/features can explicitly grant an additional Action.

Therefore the authoritative model must support:

base Action
+
zero or more explicitly granted additional Actions

where each additional Action may have restrictions defined by the
feature/effect that grants it.

Examples include features such as Action Surge or other future
rule-defined effects.

Do NOT implement individual class features in this task unless the
existing implementation already requires a compatibility hook.

The Action Economy layer must provide the generic resource model that
those features can use later.

==================================================
5. ACTION RESOURCE CONSUMPTION
==================================================

An Action resource is consumed when a valid Action is actually taken.

Example:

Player:
"I attack the goblin."

Python determines:
- current actor is correct
- target is valid
- Action is available
- attack is legal

Then the Action is consumed and the attack is resolved.

If the attack misses:

Action remains consumed.

A miss is a valid resolution, not an invalid request.

==================================================
6. INVALID ACTIONS
==================================================

An invalid request must NOT consume Action Economy resources.

Examples:

- no Action available
- actor is not the current actor
- target is invalid
- target is not a valid Combat participant
- action unavailable to this character
- action violates an authoritative condition
- malformed request
- stale Combat state
- stale turn
- invalid session/campaign
- invalid Ready trigger
- invalid resource use

Invalid request:

NO resource consumption
NO combat roll
NO damage
NO Campaign Time advancement
NO canonical history entry
NO false success result

Preserve existing API error semantics.

==================================================
7. VALID ACTION THAT FAILS
==================================================

Strictly distinguish:

INVALID REQUEST

from:

VALID ACTION WITH UNSUCCESSFUL RESULT.

Examples:

"I attack the goblin."

valid attack
→ attack roll
→ miss

The Action is consumed.

Similarly:

valid action
→ saving throw
→ target succeeds

The Action is consumed.

Do NOT refund Action Economy resources because the mechanical result
was unsuccessful.

==================================================
8. BONUS ACTION
==================================================

A character does NOT automatically have a Bonus Action.

A Bonus Action exists only when a rule explicitly grants one.

Examples:
- class feature
- spell
- feat
- species feature
- other authoritative game rule

At most one Bonus Action can be taken on a creature's turn.

The player may choose when to use the Bonus Action during the turn
unless the specific feature defines timing.

Action and Bonus Action are separate resource types.

They are NOT interchangeable.

Do NOT allow:

Action → treated as Bonus Action
Bonus Action → treated as Action

unless an explicit rule says so.

==================================================
9. BONUS ACTION ORDER
==================================================

The player is NOT forced to use the Action before the Bonus Action.

Both sequences may be valid:

Bonus Action
→ Action

or:

Action
→ Bonus Action

unless a specific feature/rule requires a particular order.

The system must not impose an artificial:

"Action must happen first"

rule.

==================================================
10. REACTION
==================================================

A creature can use a Reaction only when an authoritative trigger and
rule allow it.

A Reaction can occur:
- during the creature's own turn
- during another creature's turn

A Reaction can be taken even if the creature has also taken:
- an Action
- a Bonus Action
- or both

Once a Reaction is used:

Reaction = SPENT

It becomes available again at the start of that creature's next turn.

Do NOT reset Reactions merely because a round number changed.

Reaction recovery is based on the creature's next turn.

==================================================
11. REACTION TRIGGERS
==================================================

A Reaction cannot be activated because:

- Qwen says it happened
- frontend displays a button
- player simply requests an arbitrary Reaction
- AI thinks the situation "feels like" a trigger

Python must determine whether the specific trigger actually occurred.

Conceptually:

EVENT
↓
AUTHORITATIVE TRIGGER CHECK
↓
REACTION AVAILABLE?
↓
REACTION LEGAL?
↓
RESOLVE
↓
REACTION SPENT

==================================================
12. READY ACTION
==================================================

Ready is an Action.

When a creature uses Ready:

Action resource is consumed.

The creature defines:

1. a perceivable trigger
2. one Action OR movement to perform in response

The Ready state must be stored authoritatively.

When the trigger occurs:

- Python evaluates whether the trigger actually occurred.
- If it did, the creature may use its Reaction.
- If it did not, no Reaction is consumed.
- The prepared Ready state expires at the start of the creature's next turn.

Do NOT allow a Ready action to prepare:
- a Bonus Action
- multiple separate actions
- multiple independent triggers with multiple responses

unless a specific future rule explicitly allows it.

==================================================
13. READY SPELL COMPATIBILITY
==================================================

Do not implement the complete Spell system here.

However, the Action Economy layer must preserve the correct hook for
a future spell system.

A readied spell is an Action-based Ready operation and must be able to
carry the required authoritative Ready metadata.

Do not invent spell mechanics.

Do not implement concentration mechanics here.

#09 Spell Scope Lock will own those details.

==================================================
14. MOVEMENT
==================================================

Movement is separate from the Action resource.

On a normal turn, a creature can move up to its available Speed.

The creature may choose whether to:

move first
or
take an Action first.

Movement may be divided around actions when the rules allow it.

Example:

Move
→ Attack
→ Move

may be legal if total movement does not exceed the creature's
available movement.

Do NOT force:

Move → Action

or:

Action → Move

as a fixed order.

==================================================
15. MOVEMENT RESOURCE MODEL
==================================================

Track movement authoritatively.

Conceptually:

movement_available
movement_used
movement_remaining

Do NOT reduce the character's permanent Speed value when movement is
spent.

Example:

Speed = 30 ft.

Player moves 10 ft.

Result:

Speed = 30 ft.
movement_used = 10 ft.
movement_remaining = 20 ft.

==================================================
16. DASH
==================================================

Dash is an Action unless another rule explicitly allows it as a
different action type.

When Dash is taken:

the creature gains additional movement for the current turn equal to
the relevant Speed used for the Dash.

Example:

Speed = 30 ft.
normal movement = 30 ft.
Dash = +30 ft.
maximum movement available this turn = 60 ft.

If another valid rule grants Dash as a Bonus Action, the same underlying
movement system must be used.

Do NOT implement a second movement system for Bonus Action Dash.

==================================================
17. MULTIPLE DASHES / EXTRA ACTIONS
==================================================

Do not hardcode:

"Dash can only happen once."

If a character has a legitimate additional Action or Bonus Action that
can also be used for Dash, the authoritative system may grant additional
movement according to the applicable rule.

The Action Economy layer must therefore support multiple movement
increases from separate valid Dash uses without duplicating movement
state.

Do NOT implement class-specific exceptions here.

Provide the generic mechanism.

==================================================
18. MOVEMENT BETWEEN ATTACKS
==================================================

If a future/current rule grants multiple attacks as part of one Attack
Action, the creature may use available movement between those attacks
when the rules allow it.

Do NOT confuse:

multiple attacks inside one Attack Action

with:

multiple Actions.

This distinction must remain explicit in the data model.

==================================================
19. SIMPLE INTERACTION
==================================================

Do NOT invent a universal "Free Action" resource.

The 2024 rules distinguish movement/communication from things that
typically require an Action, and provide the Utilize action for
nonmagical object interaction.

Therefore:

- simple movement is not an Action
- ordinary communication is not an Action
- mechanically meaningful object interaction must use the appropriate
  existing rule/action
- simple incidental interactions may remain free when no rule assigns
  them an Action cost

The system must not turn every tiny interaction into an Action.

But it must also not allow unlimited complex interactions by labeling
everything "free."

Python/rules determine the distinction.

Do NOT create a new universal "Free Action" resource.

==================================================
20. ACTION TYPES
==================================================

The Action Economy layer must support the standard 2024 Action family:

- Attack
- Dash
- Disengage
- Dodge
- Help
- Hide
- Influence
- Magic
- Ready
- Search
- Study
- Utilize

as well as:
- class features
- species features
- feats
- other explicit rule-defined actions
- monster/stat-block actions when later connected by #07

Do NOT implement every feature in this task.

The Action Economy system must provide the resource framework that
those actions can consume.

==================================================
21. ACTION-SPECIFIC RESTRICTIONS
==================================================

An Action may have restrictions.

Examples:

- Action Surge additional Action may have restricted action types.
- Haste's additional Action has restricted options.
- a class feature may provide a special Action.
- a condition may prevent actions.

Therefore do NOT represent all Actions as identical unrestricted tokens.

Conceptually:

ActionGrant
- source
- quantity
- allowed_action_types
- restrictions
- duration
- consumed

The implementation may use another structure.

The important invariant:

A granted Action can only be used according to the rule that granted it.

==================================================
22. CONDITION INTEGRATION
==================================================

Action Economy must consult the existing authoritative condition/state
system.

Do NOT duplicate condition mechanics.

Examples:

If a character is Incapacitated or otherwise unable to act according
to authoritative rules:

- Action availability must be blocked as appropriate.
- Bonus Action availability must be blocked as appropriate.
- Reaction availability must follow the condition/rule.
- Movement restrictions must follow the authoritative condition rules.

The Action Economy layer should ask:

"Can this actor perform this action?"

not independently redefine why.

#08 Death System remains authoritative for Unconscious/Dead.

==================================================
23. DEATH / UNCONSCIOUS COMPATIBILITY
==================================================

Do not redesign Death System.

However, Action Economy must correctly respect its state.

Unconscious/Dead characters must not bypass the authoritative action
guards by:

- natural-language input
- UI button
- Bonus Action endpoint
- Reaction endpoint
- Ready endpoint
- movement endpoint
- special feature endpoint

unless the authoritative rule explicitly permits that behavior.

Do not implement recovery mechanics here.

==================================================
24. RESOURCE RESET
==================================================

At the start of a creature's turn:

- base Action becomes available
- valid additional Action grants are refreshed only according to their
  source/rule
- Bonus Action becomes available if the character has a rule granting
  one
- Movement is refreshed according to Speed
- Reaction becomes available if it was spent on a previous turn
- expired Ready state is cleared

Do NOT reset:
- spell slots
- class resources
- hit points
- rest-based resources
- arbitrary feature uses

Those belong to their respective systems.

==================================================
25. TURN END
==================================================

A player may end a turn without using every available resource.

Unused:
- Action
- Bonus Action
- Movement

do NOT automatically carry into the next turn unless a specific rule
explicitly says otherwise.

Reaction is different:

If unused, it remains available until used or until its relevant turn
cycle changes according to the rules.

Ready state follows its own expiration rules.

==================================================

==================================================

Integrate with #03.

CURRENT ACTOR

Do NOT make Action Economy responsible for:
- initiative

- damage mechanics
- death mechanics.

Those remain separate systems.

==================================================
27. RESOURCE CONSUMPTION ORDER
==================================================

This is critical.

For a player request:

1. Identify intent.
2. Validate actor.
3. Validate current Combat state.
4. Validate action type.
5. Validate required resource.
6. Validate action-specific legality.
7. Resolve the actual mechanic.
8. Consume the appropriate resource as part of the authoritative
   successful action resolution.
9. Persist the result and receipt atomically.

If validation fails before resolution:

NO resource consumption.

If the valid action resolves unsuccessfully:

RESOURCE IS STILL CONSUMED.

Do not refund because an attack missed or a save succeeded.

==================================================
28. RETRY / IDEMPOTENCY
==================================================

Use the existing action receipt mechanism.

If:

action_id = ABC

already resolved:

retry ABC
↓
return same receipt/result

Do NOT:
- consume another Action
- consume another Bonus Action
- consume another Reaction
- move again
- reroll
- trigger Ready again
- advance Combat twice
- advance Campaign Time twice.

If the same action ID is used with materially different payload:

preserve the existing conflict/409 behavior.

Do NOT create a second idempotency system.

==================================================
29. NATURAL LANGUAGE + ACTION ECONOMY
==================================================

Natural language remains a first-class player interface.

Examples:

"I attack the goblin."

"Önce 10 feet geri çekilip sonra saldırıyorum."

"Bonus action olarak Dash kullanıp sonra saldırıyorum."

"Bu yaratık yanıma gelirse Ready ile saldıracağım."

Python must translate/validate these against authoritative Action Economy.

Qwen may help understand intent.

Qwen must not grant the requested resources simply because the player
said they have them.

If a player says:

"İki kere bonus action kullanıyorum."

and only one is legal:

Python rejects the second.

The narration must reflect the verified result.

==================================================
30. NATURAL-LANGUAGE FLEXIBILITY
==================================================

The system should preserve player freedom.

Do NOT force players to use exact command syntax.

These should be interpreted consistently when possible:

"I move behind the goblin and attack."

"I attack, then step back."

"I dash toward the door."

"Bonus action Dash, then attack."

However, flexible language must never bypass mechanical validation.

Natural language improves input freedom.

It does NOT create rule freedom.

==================================================
31. UI CONTRACT
==================================================

Do not redesign the final Combat UI in this task.

future UI layer (#12).

The API should be able to communicate, where applicable:

- Action available
- additional Action grants
- Bonus Action available
- Reaction available

- Ready state
- legal/illegal action information
- relevant restriction/reason.

The frontend may use this information to enable/disable buttons.

Frontend must never calculate the truth itself.

==================================================
32. NO BUTTON AUTHORITY
==================================================

A button being enabled does NOT guarantee the action is valid at the
moment it is submitted.

The server must revalidate every action.

Example:

UI shows:

[Attack]

Another event changes the actor's state before the request resolves.

The server rejects the stale/invalid action.

Frontend state is presentation only.

==================================================
34. SAVE / RESUME
==================================================

Active Combat Action Economy state must survive save/resume.

If saved:

Round 2
Current actor = Player
Action = spent
Bonus Action = available
Reaction = spent
Movement remaining = 10 ft
Ready = none

then resume must restore the same authoritative state.

Resume must NOT:
- refresh Action early
- refresh Bonus Action early
- refresh Reaction incorrectly
- restore movement incorrectly
- reroll Ready state
- duplicate an already resolved action.

==================================================
35. PERSISTENCE FAILURE
==================================================

If a valid Action resolves but the authoritative persistence transaction
fails:

Do NOT report success.

Do NOT allow Qwen to narrate the result as canonical.

Do NOT leave a half-consumed resource state.

Use the existing transaction/rollback mechanism.

Do NOT create a new persistence architecture.

==================================================
36. SESSION ISOLATION
==================================================

Action Economy is campaign/session scoped.

Player A cannot:
- spend Player B's Action
- consume Player B's Reaction
- trigger Player B's Ready state
- modify Player B's movement
- replay Player B's action receipt.

Frontend filtering is insufficient.

Python must enforce isolation.
