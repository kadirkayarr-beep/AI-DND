============================================================
PRIMARY GOAL
============================================================

After #11, AI-DND must have one explicit persistence/idempotency contract:

A successfully committed gameplay action must survive:

- duplicate request
- response loss
- retry
- save/resume
- process restart
- session recreation

without becoming a second gameplay action.

A failed persistence attempt must not leave partially committed canonical
game reality.

Different campaigns/sessions must never leak state, receipts, RNG, actions,
or canonical results into each other.

Persistence must preserve Python-owned game reality.

============================================================
ARCHITECTURAL INVARIANT
============================================================

PYTHON DECIDES GAME REALITY.
LORE AUTHORITY DECIDES SETTING REALITY.
CAMPAIGN EVENTS CREATE CAMPAIGN CANON.
QWEN UNDERSTANDS INTENT, USES VERIFIED CONTEXT, AND TELLS THE STORY.
FRONTEND PRESENTS REALITY.

Persistence is canonical infrastructure.

Python/server-side persistence owns durable game state.

Qwen must never decide:

- whether state was saved
- whether an action already occurred
- whether a receipt exists
- whether a retry is a replay
- RNG continuation
- rollback
- campaign/session identity
- persistence recovery

Frontend must never decide these either.

Preserve:

- maximum 2 model calls per player turn
- deterministic fallback after rejected narration
- no model retry after rejected narration
- model prose cannot mutate canonical state

============================================================
ESTABLISHED IDEMPOTENCY CONTRACT
============================================================

These are already locked project decisions.

Do NOT silently redefine them.

1. action_id identifies the gameplay action for retry/idempotency purposes.

2. The same action_id + the same canonical request must return the same
   authoritative resolution.

3. Replaying that request must NOT:

   - roll dice again
   - consume RNG again
   - consume Action/Bonus Action/Reaction again
   - move again
   - damage again
   - heal again
   - spend a spell slot/resource again
   - advance Campaign Time again
   - trigger another scheduled event
   - add inventory/reward again
   - advance a quest again
   - apply another death-save result
   - duplicate death/rollback/recovery
   - duplicate monster resources
   - duplicate journal/campaign events
   - create a second canonical action

4. The same action_id reused for a DIFFERENT canonical request must be
   rejected.

It must NOT:

- replay the old result as if it belonged to the new request
- execute the new request
- silently overwrite the old receipt

5. Idempotency identity must remain isolated by the proper campaign/session
   ownership boundaries.

The same identifier in campaign A must not replay or affect campaign B.

6. resolution_id, where currently used, remains an authoritative resolution
   identity and must not be casually collapsed into action_id if production
   distinguishes them.

Inspect actual production semantics before modifying identity structure.

IMPORTANT ROLLBACK DISTINCTION
============================================================

Do NOT accidentally merge two different rollback concepts.

A) FAILED-PERSISTENCE / FAILED-AUTOSAVE TRANSACTION ROLLBACK

If an action has not been successfully committed because persistence failed,
the runtime must not remain partially mutated.

Restore the authoritative pre-action runtime state as required by the
existing transaction contract, including relevant:

- HP/state
- resources
- action economy
- Campaign Time
- RNG
- receipts
- events
- spell slots
- monster resources
- other action-owned mutation

A retry may then legitimately execute the action.

B) NORMAL-MODE DEATH CHECKPOINT ROLLBACK

This is an already locked #08 gameplay mechanic.

Do NOT redesign it.

Normal death rollback restores its defined gameplay checkpoint state but
intentionally follows the existing #08 semantics for receipts/RNG.

Do not make Normal death rollback behave like failed persistence merely
because both use the word "rollback."

Preserve #08 exactly.
