# AI-DND #51 — Connect Supported Ambient Events to the Game Screen

Living World V2.1 authoritative ambient-event outcome boundary has now been implemented.

The backend currently supports a very narrow authoritative outcome:

BLUE ambient event
→ player interaction
→ Python-authoritative validation
→ existing temporary scene referent promotion
→ canonical NPC
→ persistence

The backend endpoint is:

POST /api/game/sessions/{session_id}/ambient-events/{event_instance_id}/actions

Supported actions:

- interact
- observe

Supported structured results:

- APPLIED
- REJECTED
- NO_EFFECT
- ALREADY_APPLIED

The browser UI was intentionally not changed during V2.1.

This task (#51) is ONLY to expose this already-existing capability in the game screen.

DO NOT expand the gameplay system.

============================================================
6. ACTION IDENTITY
============================================================

Every intentional player action must have a UUIDv4 action_id.

For example:

player clicks Interact
→ generate UUIDv4 action_id
→ send request

player clicks Observe
→ generate a separate UUIDv4 action_id
→ send request

IMPORTANT:

Retries of the SAME request must reuse the SAME action_id.

Do not generate a new action_id merely because:

- the request is retried
- the network fails
- the query is refreshed
- React rerenders
- the component rerenders

Do not use random IDs as React render state.

Keep action identity stable for the lifetime of the pending/retry operation.

A deliberate new player action is a new action_id.

============================================================
9. NO OPTIMISTIC STATE MUTATION
============================================================

This is critical.

The frontend must NOT assume:

"Interact" means NPC created.

The frontend must NOT:

- directly add an NPC
- directly modify the scene
- directly modify inventory
- directly modify quest state
- directly modify memory
- directly modify journal
- mark an event completed locally
- fabricate a successful result

The server is authoritative.

Flow:

PLAYER CLICK
↓
POST ACTION
↓
SERVER VALIDATES
↓
SERVER RETURNS STRUCTURED RESULT
↓
CLIENT DISPLAYS RESULT
↓
CLIENT REFRESHES SERVER STATE

============================================================
10. RESULT HANDLING
============================================================

Handle all four backend result statuses:

APPLIED
REJECTED
NO_EFFECT
ALREADY_APPLIED

Do not treat every HTTP success as gameplay success.

The structured response must be interpreted.

Player-facing text should be natural and understandable.

Do not expose internal implementation jargon such as:

- UUID
- event_instance_id
- transition_id
- canonical journal ID
- database error
- stack trace
- internal reason codes

The frontend may use the structured status internally.

Map it to appropriate player-facing feedback.

For example, conceptually:

APPLIED:
the interaction had a real verified effect.

NO_EFFECT:
the action was valid but produced no lasting change.

REJECTED:
the requested interaction could not be performed.

ALREADY_APPLIED:
the event has already been resolved.

Do not invent gameplay consequences in these messages.

============================================================
11. REFRESH AFTER RESULT
============================================================

After receiving an authoritative result:

refresh the existing game state from the server.

Do not locally mutate the game state to imitate the result.

The UI should reflect whatever the server now considers canonical.

If the server promotes the BLUE referent to a canonical NPC:

the refreshed scene should show that canonical state.

If the server rejects the action:

the existing scene should remain authoritative.

Use the existing query invalidation/refetch pattern already used by game-browser.

Do not create a second game-state cache.

============================================================
12. LOADING / DUPLICATE CLICKS
============================================================

While an action request is pending:

- disable the relevant action controls
- prevent accidental duplicate submissions
- show a minimal loading state

Do not create multiple action IDs for the same pending request.

If the request needs retrying:

reuse the same action_id.

Do not silently retry with a new action_id.

============================================================
13. FAILED NETWORK REQUESTS
============================================================

A network failure is NOT the same thing as:

REJECTED
NO_EFFECT
ALREADY_APPLIED

Do not fabricate a gameplay result when the server response is unavailable.

Show a neutral player-facing retry state.

If retrying the same request:

reuse the same action_id.

After retrying, use the actual authoritative server response.

Do not optimistically update state.
